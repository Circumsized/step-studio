# 一手实践：X 资深开发者与国内外大厂

前面四份工作流的对策，多数能追到一个具体的人或一家的具体数字。这份是那些一手来源的集中档案——谁说的、在什么场合、数字是多少、以及它对应本项目的哪条对策。

标注了来源性质：**一手**（本人原帖 / 官方博客 / 官方财报或大会演讲 / 自家论文）和**二手**（媒体转述）。二手材料只用来定位一手，不用来支撑结论。

## 一、X 与个人开发者

### Geoffrey Huntley — Ralph Wiggum Technique（一手）

澳大利亚工程师，畜牧从业者。2025 年 7 月在个人博客发《Ralph Wiggum as a "software engineer"》命名此法；源头是更早墨尔本 Web Directions 大会上的演讲。核心就一行：

```bash
while :; do cat PROMPT.md | claude-code ; done
```

每轮从全新会话开始，读文件和代码判断进度，干一点，把进度写回文件。外部校验条件（测试通过）满足才停。

**四条可直接用的**：

1. **「这种技术在不确定的世界中是确定性糟糕的。可预测的失败胜过不可预测的成功。」** 这是整个方法的自我定位——它不是「更聪明」，是「更可预测」。
2. **完成条件必须具体到机器可判。** 社区总结的教训：*「做完这个功能」不行，Claude 会自己说服自己已经完成了。要写「所有 CRUD 端点可用，测试覆盖率超过 80%，README 包含 API 文档，完成后输出 COMPLETE」。条件越模糊，它越会找理由提前收工。*
3. **成本是实的。** *「这些是精挑细选的成功案例。对于每个 overnight 胜利，都有循环在未收敛的情况下耗尽了迭代次数。失败的尝试仍然花费金钱。」* 本次会话 $1177 就是这句话的实例。
4. **适用范围**：大型重构、框架迁移、依赖升级、批量操作、测试覆盖率补充——共同点是**有明确完成标准的机械工作**。需要大量判断的，Huntley 自己说坚持用基础方法。

**实证规模**：Huntley 用一个 prompt 连续跑三个月，产出 Cursed——一门功能完整的编程语言，LLVM 编译到原生二进制，有标准库和部分编辑器支持。YC 黑客松上有团队用此法 overnight 交付 6+ 仓库，API 成本 297 美元。

**机制**：Claude Code 官方 `ralph-wiggum` 插件由 Anthropic 工程师 **Daisy Hollman** 做，用 Stop hook（退出码 2）拦截 Claude 的退出、重新注入原 prompt。`/ralph-loop "<task>" --max-iterations 50 --completion-promise "<条件>"`。

对应：[`agent-loop.md`](agent-loop.md) LOOP-3（退出条件具体化）、LOOP-1（轮次上限）、[`afk-development.md`](afk-development.md) §1.3（金额上限）。

### Addy Osmani 与 Requesty — Loop Engineering 零件清单（一手，X）

两人独立列出几乎相同的清单。Osmani 的说法是**「五个原语 + 一个状态存储」**。LangChain《The Art of Loop Engineering》给的是四层栈，从里到外：

```
prompt engineering → context engineering → harness engineering → loop engineering
```

反过来说：**prompt 写得模糊、context 配置混乱，Harness、Loop 搭得再漂亮也救不了**——因为循环每一轮真正喂给模型的，最底层还是 prompt 和 context。

Claude Code 的 loop 命令时间线（官方）：`/loop` 2026-03-07、`/schedule` 2026-04-14、`/goal` 2026-05-11、`/workflows` 2026-05-28。Anthropic《Getting started with loops》给了官方分类。判断标准很简单：**只要 AI 在重复同一个 cycle——做一步 → 看结果 → 决定下一步 → 再来一轮 → 知道达到条件后退出——就是个 loop**，区别只在谁来发起下一轮。

对应：四层栈是「先修哪层」的排序依据。本项目当前缺的是 harness 层（测试超时、平台 job 计数），不是 loop 层。

## 二、国内大厂

### 字节跳动 BitsAI-CR（一手，自家论文 arXiv 2501.15134）

**这是全部材料里对 `code-review.md` 最有价值的一条。** 字节首次公开内部代码审查系统，服务超 1.2 万周活开发者。

数字：**审查准确率 75%**，评论过时率 26.7%。

三大工业级挑战（他们自己总结的）：**评论准确性不足、价值有限的评论过多、缺乏系统化的改进机制。**

**两阶段「识别 + 验证」架构**：

| 阶段 | 做什么 | 关键细节 |
| --- | --- | --- |
| RuleChecker | 识别 | Tree-sitter 做精确代码块识别和函数边界检测组成上下文；基于内部 **219 条多维审查规则**（代码缺陷、安全漏洞、可维护性、性能 4 大维度）；LoRA 微调 Doubao-Pro-32K-0828 生成评论 |
| ReviewFilter | 验证 | **另一个**微调模型对 RuleChecker 的每条输出做二元判断（保留 / 不保留）加判断依据 |

三个值得抄的细节：

1. **单一模型微调不够。** 他们试过优化训练样本、强化学习，收效都有限，最后靠引入**独立验证模块**才把准确率做上去。这和「干活的 agent 不给自己打分」是同一件事。
2. **ReviewFilter 的推理模式有优劣。** 对比「直接结论」「推理在前」「结论在前」，**「结论在前」准确率 77.09% 且推理时间短**——先给判断再给理由，比先推理后结论好。
3. **动态规则黑名单**：实时剔除低效规则，让审查标准与企业实践动态对齐。

还有一个原创指标 **Outdated Rate（评论过时率）**。起因很实在：*开发者面对大量审查评论时往往采取完全忽视的策略，而初期的不准确评论更会严重损害用户信任*——所以他们把**准确率作为首要优化目标**，而不是召回率。

**这和阿里「宁可少报，不报假警」是同一个取舍，两家独立收敛到它。**

对应：[`code-review.md`](code-review.md) REV-2（找问题/挑刺分组）、REV-5（用事故校准 = 动态规则黑名单的组织版）。

### 字节跳动 洪定坤（技术副总裁）Force 2026 + TRAE 团队实验（一手，大会演讲）

**900 次极限对撞实验**——选一个中等复杂度真实业务需求（豆包，含复杂视频预览、时序调整），3 个主流 Coding 模型 × 3 个主流 Agent 框架，相同 Prompt 各跑 100 次：

| 维度 | 纯对话 | 加 Harness 基建后 |
| --- | --- | --- |
| 功能正确率 | 80–90% | 接近 90% |
| **软件工程可交付性**（UI/交互/性能/可维护性） | **40–60 分，普遍不及格** | **80 分，达到上线标准** |

**核心结论：AI 写的代码「能用」和「能上线」之间隔着一条很宽的沟。** 典型缺陷：不复用既有组件、异常捕获不规范、改动震荡历史遗留功能、不符合团队规范。

**Vibe Coding 省掉的两件事**（因为省掉后 Demo 照样跑得通）：**防御性编程**（替意外情况做准备）和**异常处理**（出错时有预案而不是当场崩溃）。

**Harness 基建四件套**：上下文工程、架构约束、团队知识沉淀、技术债梳理。

**数据悖论**：TRAE 团队本身做 AI Coding 工具、用得最激进，过去半年 >90% 代码由 AI 写，人均需求吞吐只提升 60%。10 倍速度 → 1.6 倍效率。洪定坤自己的判断：*这些数字不代表他们做得有多好，恰恰相反，用得越多越能感受到问题在哪。*

还有三条风险是本次会话真实遇到的：**Token 刺客、Agent 失控、盲目重调**——原话称之为「真实的财务和系统灾难」。

对应：[`afk-development.md`](afk-development.md) §1.3（金额上限，防 Token 刺客）、[`code-review.md`](code-review.md) REV-1（确定性门禁覆盖不到必须人看的，正是交付性那 40 分）。

### 腾讯 2025 研发大数据报告（一手，官方报告）

- 90%+ 工程师用 AI 编程助手（自研 CodeBuddy，混元大模型）
- 50% 新增代码 AI 辅助生成，整体研发效能 +20%，编码时间平均缩短 40%
- **AI 代码评审参与度 94%**；**28% 缺陷由 AI 直接发现并修复**；**代码评审有效问题检出量增长 44%**
- 推进方式：写进 KPI，配合内部培训、评选 AI 先进典型、token 补贴

汤道生（高级执行副总裁）2026-06 补了一条关键的反面数据：**AI 生成代码效率提升 47%，但修代码时间反增三倍。**

对应：[`code-review.md`](code-review.md) REV-2。「修代码时间反增三倍」是 CI-1 分层和 REV-4 关门纪律的直接理由——省下的编写时间不能变成三倍的修复时间。

### 快手（一手，GitHub / OpenHarmony 开源）

鸿蒙团队：AI 代码生成率 80%，团队人效提升 1.7 倍；**AI 产出的测试用例采纳率 84%**，**AI 排障修复建议采纳率 73%**；性能优化从「两人一周」降到「半天」。

他们把多款 AI-Coding Skills 开在了 GitHub 和 OpenHarmony 的 SKILL 广场。这个动作本身是论点：AI 编程的工程化能力不是秘密武器，是公共基础设施。

对应：REV-5。Skills 化 = 把一次提效变成可复用的方法，这正是 `design/workflow/` 在做的事。

### 百度（一手，财报 + 百度世界大会 + 副总裁陈洋演讲）

文心快码：每日新增代码中 AI 占比超 43%，整体提效超 20%。**上线前漏洞修复率提升 47%**，安全响应与漏洞修复从小时级降到分钟级。

按研发阶段部署专属智能体：产品文档、编码、安全、单测、合规、部署。

组织侧（百度世界 2026「智能组织」）：日活跃智能体从约 5000 涨到 3.7 万，每周有效任务从 8.4 万涨到 100 万+；4300 个 Workspace，2 万+ 组织 Skill。数字人创新业务部 Q3 做 564 次产研迭代，形成 130 个 Skill 和 729 篇组织资产，人均吞吐 +125.3%，交付周期 -28.8%。

**Skill 的定义值得照抄**：*一个团队完成某类工作的方法。它可能包含操作顺序、业务规则、检查标准和历史经验。* 智能体数量只是一方面，**能留下多少可复用的方法同样重要**。

对应：`design/workflow/` 这份文档本身就该按 Skill 组织，不是按会议纪要。

### Sonar《2026 开发者调查报告》（一手，调查报告）

**72% 的开发者每天用 AI 编程工具，58% 的公司没有任何 AI 代码治理策略。**

这一条是全部材料里最该贴在墙上的。本项目现在处于那 58%——本次会话为变绿把三个测试套件关门，就是没有治理策略的表现。

## 三、国际大厂

### Spotify — Honk 系统（一手，工程博客/访谈，最详细的一手国际案例）

**73% 的 PR 由 AI 生成，2900 名工程师。**

关键事实按时间线：

1. **前身是跑了五六年的代码自动化基础设施**（「代码舰队管理」），早期一年最多 10 次全库框架迁移，每次数月。后来撞到静态分析天花板——替换一个有 5 种调用方式的 API 要写几千行脚本。大模型只是最后补上的那块拼图，Honk 前后迭代近 8 个版本。
2. **独立 AI 评估器把 PR 通过率从 20% 拉到 80%。** 这个模块专门检查大模型生成的代码是否符合规范。**Claude 4.5 发布后模型自身能力足够覆盖自查，评估器才被移除。**
3. **在大规模引入 AI PR 之前，就把全公司代码库拆成数千个权责清晰的独立组件，每个组件的自动化测试覆盖率被要求达到极高标准。** 之后大部分 AI 生成的 PR 不需要人工审核，系统自动合并，相关团队甚至看不到这些 PR。
4. 现在每天 4500 次生产部署，功能从想法到上线压缩到 1 小时，质量指标保持稳定。PR 提交频率 +75%。

首席架构师 Niklas Gustavsson 的比喻：**AI 编码代理是「大脑」**（自然语言 → 代码变更），**车队管理系统是「肌肉」**（通过自动化 PR 在数千个仓库里安全跑这些变更）。

**最重要的一条**：*代码越标准，智能体表现越好。如果同一个功能在代码库里存在 10 种不同的实现方式，大模型反而会陷入混乱，不知道该参考哪一种规范输出结果。* 统一工具栈、一致编码规范、清晰组件边界——这些传统软件工程最基础的要求，在 AI 时代成了绝大多数企业达不到的高门槛。

对应：CI-3（平台 job 数测试数）和 REV-1（确定性门禁）就是「肌肉」。本项目的 `scripts/architecture.test.mjs` 等已经是肌肉，缺的是把它当肌肉用。

### Google（一手，CEO 皮查伊 + 财报会）

- 内部**75% 新代码由 AI 生成**（18 个月前是 25%，指数级演进），工程师角色转向「审核与把关」
- 一次复杂代码迁移中，智能体 + 工程师协相比一年前纯人工**快 6 倍**
- 把 AI 工具使用目标纳入部分工程师年度绩效评估
- 2026 年资本支出计划 1850 亿美元，配套第八代 TPU 与 Gemini Enterprise Agent Platform
- 插曲：DeepMind 部分员工获准使用竞品 Claude Code，内部引发紧张——**一线工程师的工具选择优先于生态推广**

对应：REV-3 的风险分级。75% AI 代码 + 工程师转审核，意味着本项目「Windows 握手没验过」这类缺口在 Google 模式里是不被允许上线的。

## 四、这些一手材料改变了哪几条对策

读完一手材料后，对前四份文档的实质修正：

1. **`code-review.md` REV-2 的两阶段结构有了直接范本。** BitsAI-CR 的 RuleChecker + ReviewFilter 就是 fp-check 的 Phase 1–4 + Gate Review 的工业版。补一条：**ReviewFilter 用「结论在前」模式，准确率 77.09% 优于「推理在前」。**
2. **新增指标 Outdated Rate。** 本项目审查评论没有「过时率」概念——一条关于已删代码的评论和一条真问题同样显示在 PR 里。BitsAI-CR 因为准确率损害信任才引入它。
3. **Spotify 的评估器 20%→80% 是一条被验证过的单点杠杆。** 本项目 `npm run check` 已经有这个形状，但没人在它变红时优先修它——本次它就是红了一路。
4. **字节 900 次实验给出了「能用 vs 能上线」的量化差距（40–60 分 vs 80 分）。** 这条要写进 REV-1：确定性门禁覆盖不到的那 40 分，正是必须人工看的部分。
5. **Sonar 的 72%/58% 是立项理由。** 本项目现在没有 AI 代码治理策略，这份文档就是补那 58%。
