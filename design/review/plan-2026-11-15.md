# Review 与测试方案（2026-11-15）

> 依据：四路联网检索的权威资料（代码评审实证、测试有效性实证、Rust/Tauri 测试实践、
> 本地优先桌面应用安全评审）。每条设计选择附证据；**证据不支持的也单列**，避免把民俗当依据。
> 全程应用 ponytail（最小够用）、stop-that-shit（不为假想需求设防）、antislop（过滤器）。

## 0. 四份研究独立收敛到的同一结论

**帧协议 / 子进程边界是本项目最高风险面，而人眼 review 和现有单测都到不了它。**

| 来源 | 证据 |
|---|---|
| Chromium OS 案例对照研究（Paul, Turzo, Bosu, ICSE 2022） | 404,878 次评审中，**88.89% 的输入验证缺陷、87.88% 的访问控制缺陷逃过了评审**——而该项目评审是强制的 |
| AFLNet（Pham, Böhme, Roychoudhury, ICST 2020） | 有状态模糊测试在两个流行协议实现里找出 **2 个 CVSS 9.8**；论文明说单测覆盖不了状态**转移** |
| Rust 测试实践简报 | 「帧解析器上的一条 proptest 属性是整个代码库里性价比最高的新增」 |
| 安全简报 | 帧解码器是「单一 choke point、纯函数、手写 u32 长度到分配路径」——最值得模糊测试的目标 |

三条独立的线指向同一个文件。这不是巧合，是本项目结构的必然：壳 → daemon → adapter → CLI，
每一跳都是一个协议边界，而现有 346 个 Rust 测试几乎全在测「结构正确」而非「对抗性输入」。

### 2.1d T4 执行结果：65 个函数里 22 个的契约无人断言（34%）

**方法**：用 TypeScript AST 找出 15 个核心逻辑模块里 65 个「有块体、有显式返回类型标注、
不是类型谓词」的导出函数，逐个把函数体换成 `return (null as unknown as <声明类型>)`，
每换一个跑一次全量 953 个测试。铸造到声明类型是必须的——直接 `return undefined as never`
会把返回类型也改掉，调用方跟着炸，那就分不清是"测到了"还是"编不过"。

**结果：22 / 65 = 34%**，变异后 953 个测试全绿（该数字是当时的基数；现为 963），
即没有任何测试断言这些函数的返回值。

**这个 34% 不能和 PS_RATE 并列**（2026-11-17 审评纠正，我原先写了"假设成立"）：
65 的分母是"有显式返回类型标注的导出"，既不是"导出"也不是"方法"——标注过滤
悄悄丢掉了推断返回类型的导出。两者测的不是同一个总体，"假设成立"是过度声称。
可说的是：在**这一个**子总体里，22/65 的返回值无人断言。

**"红"证明的是敏感，不是被钉住的契约。** `toBeTruthy()` / `toBeDefined()` /
`not.toBeNull()` / `expect(x.length).toBeGreaterThan(0)` 在 null 变异下都会红，
于是那些函数被算作"已断言"。崩溃敏感也算：一个让下游消费者抛异常的 null 返回
同样转红。所以 43 个"被抓住"里，有一部分在论文的意义下仍是 pseudo-tested 的。
§2.1c 为 Rust 那条画过这条线（"不 panic" vs "拒绝"），这里没有应用它。

**对 `void` 与有副作用的导出，这个变异是副作用变异而不是返回变异。**
`beforeConversationReflowChange(): void` 派发 window 事件；
`restoreConversationReflowAnchor()` 写 `scrollTop` **并且**返回布尔。
清空函数体两者都没了。于是"绿"的含义比标题更弱：**没有测试断言它的返回值，
也没有测试断言它的副作用**。而"红"只说明"某个可观测量变了"，可能是副作用：
一个断言 `scroller.scrollTop` 的测试会红，而"有没有成功恢复"这个布尔完全没被钉住。

**扫描的单位是导出边界，而三个 bug 全在私有 callee 里。** `deriveHero`、
`runtimeCheck`、labelFor、`terminalFromState` 都不导出，扫描看不见它们。
所以这次扫描是**指针，不是探测器**——bug 是读出来的，不是变异出来的。

| 文件 | pseudo-tested / 可变异 |
| --- | --- |
| `conversation/conversationReflow.ts` | **7 / 11** |
| `diagnosticsModel.ts` | **7 / 13** |
| `sessionLifecycle.ts` | 4 / 6 |
| `composer/serialize.ts` | 2 / 14 |
| `composer/mentions.ts` | 1 / 5 |
| `conversation/rowHeightCache.ts` | 1 / 3 |
| 其余 8 个文件 | 0 |

集中在两个模块：reflow 交易（7）和 diagnostics 的格式化函数（7）。

**失败模式，以及它不证明什么**：这 22 个不是 22 个 bug。以 reflow 为例，它那 2 个测试是
**行为式**的——派发 `CONVERSATION_LAYOUT_BEFORE_CHANGE` / `_CHANGE` DOM 事件，断言
`pinRow` 的调用和 `isConversationReflowing()` 的布尔。那些函数在内部被调用，返回值不被断言，
所以换成 `null` 在这些测试驱动的路径上看不出区别。真正说的是：**这 22 个函数的契约，
没有任何测试断言**。对 `conversationIsFollowing` 这种谓词是覆盖缺口；对
`restoreConversationReflowAnchor` 这种返回锚点对象的，返回值错了会静默错位。

**顺着缺口挖出两个真 bug，已修**（`diagnosticsModel` 那 7 个是用户可见的诊断面板文案，
所以先读了它们，而不是只记缺口）：

1. **未知状态让整个诊断面板崩掉。** 标签表 typed `Record<Union, string>`，读起来是完备的，
   但联合类型是编译期承诺。Host 发一个这个版本没有的状态，`RUNTIME_LABEL[status]` 得
   `undefined`，`t(undefined)` 在 `path.split(".")` 抛 `TypeError`，
   `deriveDiagnosticsView` 跟着崩。13 个调用点全走这条路径。
2. **更糟的一处：未知状态被报成"运行正常"。** `deriveHero` 的兜底分支无条件返回
   `kind: "ok"`，于是任何没有分支的状态——包括未来 Host 新增的——都告诉用户一切正常。
   **fail-open**。同文件的 `runtimeCheck` 兜底已经是 `tone: "error"` + 原始值，
   只有 hero 这道漏了。

修法：`labelFor()` 助手（表里没有就回退到原始键，让运维看到 Host 实际报了什么），
加一个 `heroUnknownStatus` 的 i18n 键（zh/en 各一条），hero 在兜底前先拦住未知状态。
三条测试钉住，**两处修复分别做过变异验证**：撤掉回退 → 2 条红；撤掉 hero 分支 → 1 条红。

**继续往下读，又抓到一个挂死**（`sessionLifecycle` 那 4 个里的下游）：

`waitForCommandReceipt` **只读一次命令状态就订阅**，没有 `onState` 监听、也没有超时。
而 `hostError.ts` 的 `waitReceipt` 注释里正写着这件事：「reducer 会把 in-flight 命令标成
`outcome_unknown` 而**不发** `command.receipt` 事件——re-bootstrap、resync、
runtime epoch 变化、runtime 丢失」。这四种情况**全部**发生在订阅之后，于是那个等待
**永远不 settle**：调用方既收不到结果也收不到错误，没有退路。

同一个文件里 `waitReceipt` 早就解决了这件事（`onState` + 120 s 预算），这份拷贝没继承到。
**是活的**：`DiagnosticsPage.tsx:59`（安装/重连/重启 Runtime）、`runtimeEnsure.ts:105`、
`HomePage.tsx:1095`。

探针实测（订阅后才把状态改成 `outcome_unknown`）：`outcome -> HUNG`。

**修**：补 `onState` 监听 + 120 s 预算，超时resolve 一个 `outcome_unknown` receipt
（resolve 而不是 reject，因为每个调用方都自己查 `receipt.status`，而它们已经处理这个状态）。
四条测试，**两处分别变异验证**：去掉 `onState` → 1 条红；把默认预算改回 `null` → 1 条红
（第二条一开始没红——测试显式传了 60，动的只是默认值；补了一条用假计时器钉住默认值的才红）。

**另外两个只读没 bug**：`docIsEmpty` / `snapshotIsEmpty` 是正确的，而且
`snapshotIsEmpty` 里对 mode chip 的那个特判是**承重墙**——`serializeChip` 对 mode 返回
`""`，没有那条特判，只含 mode chip 的草稿会被判成空、发送按钮点不动。
`isNewConversationAvailable()` 恒返回 `true`、旁边那条「Host 未提供 session.create」的
不可用理由**零引用**——是个等着被信任的占位符（与已删的全零验签钥同形），但没接上线，
记此不删。

**其中一个当场修掉**：`the_probe_looks_where_the_daemon_binds` 看似测 `default_endpoint`，
实际是**拿函数和自己比**——`daemon_probe_path()` 就是 `PathBuf::from(default_endpoint())`，
两边一起变。破坏验证过：把 `default_endpoint` 换成空串，测试照绿。而它的注释正写着
"a wrong path made both sides false and the test passed"——它以为修掉了，其实没有，
只是把同构比较挪深了一层。已补两条绝对断言（端点非空、不在 shell 自己的工作区目录下），
两个方向都破坏验证过。

**同一个家族，Rust 侧还有一批弱谕言，其中一族是真空的。** 全仓扫
`assert!(...is_err())` 共 **39 处**：31 处带消息，8 处裸断言。逐处看过，
**多数是纯函数拒绝**——`ref_name("--upload-pack=evil")`、
`set_directory("somewhere/relative")`、删完条目后的 `resolve()`，这些都只可能因为
被拒而 `Err`，没有第二个错误来源，`is_err()` 就是合格谕言，不动。

**真弱的是会 shell out 的那 4 个**（`git.rs` 的 `write_tests`）：`paths_op` 虽然拒了
`../../etc/passwd`，但 **git 自己也拒**（`fatal: '../../etc/passwd' is outside repository`），
而机器上没装 git 时整条命令同样是 `Err`。三种错误同一个观测，裸 `is_err()` 分不出
是哪一种——在一台没装 git 的机器上这四条全绿，却什么都没断言我们的校验。
破坏验证：删掉 `paths_op` 的路径 guard，加强后的测试转红并报
`refused for the wrong reason: fatal: ... is outside repository`，
这正是旧断言做不了的判别。现已钉住拒绝前缀（`refusing the path` / `needs a message` /
`refusing the branch name` / `refusing the pull strategy`），提交 `7bac895`。

**顺手验了一个我以为是同族的，结果不是**：`chrome.rs` 的
`a_link_carrying_a_double_quote_is_refused` 也是裸 `is_err()`，我怀疑守卫删掉后
Linux 上 `xdg-open` 不存在会让 `spawn()` 失败、同样返回 `Err`，那它就是空转的。
实测删掉 quote 守卫，测试**转红**——这台机器上 `xdg-open` 存在（只是打印
`no method available` 并非零退出），而 `spawn()` 只看进程起没起来。承重墙，不动。

**同家族还有一族更隐蔽的：测试因前置条件缺失而静默 `return`。** 扫全仓
`#[cfg(test)]` 段，真正命中 **8 个 return 语句，分布在 7 个测试函数里**：
`git.rs` 6 处
（`let Some(root) = repo_root() else { return }`，行 1722/1738/1749/1762/1780/1841）
加 `step-studio-sessions/src/lib.rs:619` 一个函数里的两处
（`store_dir()` 为 None、`!store.is_dir()`）。
（另扫到 2 处 `let Some(..) else { return }` 在 `bridge_server.rs` 的
`dispatch` 与 `settle_prompt`——那是**生产代码**不是测试，正则误报。）

这 7 处在 CI 里都跑（CI 必然检出 git 仓库），但在无 git 的机器上**一条都不执行，
且和通过长得一模一样**——`repo_root()` 跑 `git rev-parse --show-toplevel`，
失败或空输出即 None，跳过路径上 0 处输出。刚加强的那 4 条 `write_tests` 也在这 6 处里。

**判定：不改。** 理由是场景带外——本项目自身的 git 功能就要求 git 在场，
CI 也必然在仓库里；给 6 处加 `eprintln` 或加一条「前置条件必须成立」的元测试，
是为一个不该发生的场景制造噪音，且后者会让无 git 的机器从「假绿」变成「真红」，
对一个跑不了产品 git 功能的机器没有增益。记此不删，与 S9 对 `signing.rs`
「不能删但也不接线」的处理同形。

**`signing.rs` 的删/降争论就此关闭**（2026-11-19 复核）：S9 已判「不能删」——
它握着 Rust 侧「降级被拒」属性唯一的测试，而 TS 侧那份（真正该接的）当时一条都没有。
所缺的补偿**已落地**：`packages/runtime-installer/test/update-index.test.ts`
三条（等于水位线放行 / 旧签名清单仍拒 / digest 不符拒），且已注册进
`scripts/core-suites.mjs:45`。`ed25519_dalek` 仍是全仓仅 `signing.rs` 一个使用者，
即依赖纯粹为它而存在——这一点记在此处，接线时连依赖一起评估。

**零断言测试扫描：20 个候选，20 个全是误报**（2026-11-19）。这是 pseudo-tested
最纯粹的形态，扫完的结果是本仓没有这个缺陷。三族的误报原因各不相同，但都指向
同一条：**断言不住在 `it`/`#[test]` 的函数体里**。

| 数量 | 位置 | 断言实际在哪 |
| --- | --- | --- |
| 15 | `apps/desktop-tui/tests/golden.rs` | 共享助手 `assert_golden()`：对 fixture 文件 `assert_eq!`，缺 fixture 直接 `panic!` |
| 4 | `conversation/markdownBlocks.test.ts:60-71` | 助手 `replay()` 的循环里，每帧一次 `expect(...).toEqual(...)` |
| 1 | `a11y-keyboard.test.tsx:72` | 第 100 行 `expect(missing, ...).toEqual([])`——是我的括号匹配被 `=>` 带偏才漏看 |

`golden.rs` 那 15 处还值得单独说一句：`UPDATE_GOLDEN` 是 opt-in 而非自动，
注释写明了理由——「会自己改写期望的测试无法失败」。这个设计是对的，
所以那 15 个测试不是「没有断言」，而是「断言在夹具里，夹具只能手工更新」。

这条与 T4 的结论同构：**扫描是指针，不是探测器**。它找到的 20 个里没有一个
真缺陷，但正是逐个数过来才敢这么说——而数过来的成本比扫一眼高一个量级，
这就是为什么这类扫描的结果必须连误报理由一起记，否则下一个人会重新扫一遍。

**第三种弱谕言：测试名声称了它不断言的属性**（2026-11-19）。前两种是「断言太弱」
（`is_err()` 分不清是谁拒的）和「根本没跑」（前置条件缺失就 return），第三种是
**断言是对的，但名字许诺了更强的东西**，于是读代码的人会以为那道防线存在。

抓到的是一个安全属性：`handshake.rs` 的 `the_proof_comparison_does_not_short_circuit`
断言了相等输入、每个单字节差异、长度差异、空串都被正确分类——**这些全是正确性，
没有一项是时序**。破坏验证：把 `same_bytes` 的函数体换成提前退出的循环，
功能完全等价，而**该模块 8 条测试全绿，包括这一条**。也就是说常量时间性
（`verify_proof` 用来防时序侧信道的那道防线）在套件里没有任何检查。

已处理：**不加计时测试**（计时断言在 CI 里必然 flaky，而 flaky 测试比没有测试更糟——
它训练所有人忽略红色），改为把测试改名为
`every_byte_and_the_length_of_the_proof_are_compared`，并把边界写进注释：
常量时间性是实现的性质，靠读 `same_bytes` 核实，不靠测试。`same_bytes` 本身没错也没动。

同一轮还重做了两次方案声称过、但本会话未亲眼见的破坏验证，都成立：
`verify_proof` 改成恒真 → `a_proof_computed_with_the_wrong_token_is_refused` 转红，
其余 7 条照绿（确认它是 `verify_proof` 的承重测试）。

**仍然没做**：没有给其余 21 个补测试。按 `AGENTS.md` 的测试哲学（只测用户能感知的行为和
真实出过的 bug，不为内部结构写成套测试），先记录缺口和集中点，补哪些由项目负责人定——
尤其 `diagnosticsModel` 那 7 个是纯格式化函数，用户看得见，优先级高于 reflow 的内部谓词。

**顺带抓到一个 flaky 测试**（这是执行 T4 的方式逼出来的）：`SubagentsPanel.test.tsx` 的
「persists the disabled state through agents.definition.configure」在**未变异**的全量跑里
超时失败（5170 ms vs 默认 5000 ms 预算），单独跑 4/4 通过——只在全量并行抢 CPU 时超时。
已按仓内既有先例（`RuntimeSettings.test.tsx:142`、`SettingsPage.test.tsx:210`）给它加
`, 15000`。修复后连续 7 次全量跑 953/953 全绿。

### 2.1c 变异测试翻出了我自己新测试里的缺口

加「对抗性输入不 panic」那条测试时，先做了三次破坏。前两次一次是等价变异
（`buffer.len() < 4` 改 `<=`，合法帧永远更长所以行为不变）、一次被抓到。
**第三次是关键**：把 `payload_length > MAX_FRAME_BYTES` 的守卫禁用，
**没有任何测试转红**。

原因在我自己的测试：它只断言「不 panic」，然后把 `push` 的返回值丢掉了。
而禁用该守卫后行为差异是 `Err(TooLarge)` 变成 `Ok([])`——超大长度只会让解码器
继续等永远不会来的字节，既不 panic 也不出错。所以我的测试看不出区别。

**这意味着 `MAX_FRAME_BYTES` 这个上限此前是一个没有任何测试能丢失的控制。**
补上对拒绝的显式断言后，同一次破坏立刻转红：
`a frame over the cap must be refused, got Ok([])`。

这是 Vera-Pérez 等人的发现用在了我自己刚写的测试上：**覆盖率够高、
断言仍然可能为空**。也说明「不 panic」和「拒绝」是两个不同的属性，前者覆盖不了后者。

### 2.1b T3 的实际形态：撤回了 proptest

原计划写 proptest 属性。加上之后 `Cargo.lock` 从 **595 → 608 个包**，于是按 ponytail 的梯子
重算：这 13 个包买到的主要是** shrinking**（最小复现），而 round-trip 属性用一张
**精心挑选的丑 body 表**覆盖得更好——proptest 自己的限制页就写「传统单测以智能挑选的用例
对许多类问题仍然必要」，且「大空间里极不可能找到单值边界情况」。随机 body 几乎永远不会
包含嵌套转义或半个代理对。**撤回依赖，写表。**

两张表：

- `every_body_the_codec_carries_survives_a_round_trip`：10 个 body（空对象、null、转义、
  unicode、深层嵌套、f64 边界数、4096 长串、200 键），每个都校验 payload/header 长度前缀
  自洽、往返后 body 相同、epoch/version 保留、声明的 `body_length` 等于实际编码长度。
- `a_frame_split_at_any_boundary_decodes_the_same`：在**每一个**字节边界拆分。
  原有测试只在一个硬编码偏移拆——而增量解码器缓冲算术的 off-by-one 只在特定拆分点暴露，
  拆一次是抛硬币。

**非空泛验证（第一次尝试是失败的，值得记）**：先把 `buffer.len() < LENGTH_PREFIX_BYTES`
改成 `<=`——**等价变异**， buffer 恰为 8 字节时只是更保守，而合法帧永远 >8，所以全部测试
仍然绿。这证明不了任何事。换成真正可观测的变异（`body_length: body_bytes.len() + 1`），
三个帧测试（含原有的）全部转红。

## 3. 安全方案

### 3.1 威胁模型

用 **OWASP Threat Modeling Cheat Sheet** 的四问四步，不用工具：Microsoft TMT 是 Windows-only
且威胁生成规则是 web/cloud 形状的，2-3 人团队会花时间跟工具吵架。产物就是下面那张表：
按信任边界编号，每条带 **response**（Mitigate / Eliminate / Transfer / Accept，每个 Accept 写理由），
Mitigate 行末列对应的可测需求。边界编号与表中 `边界` 列对应，威胁编号 `TH1`–`TH13`。

**必须显式加入的两个威胁源**（STRIDE 的词汇是网络形状的，不会自己浮现）：
1. **另一个本地用户账户**（共享 Windows/macOS 机器）
2. **同账户下的另一个进程**（用户装的任何应用、能拉起 helper 的浏览器内容）

信任边界（Tauri 自己的安全模型给的骨架）：WebView → Tauri core(Rust) → daemon(socket)
→ adapter(stdio JSONL) → OS keystore / 加密文件 → 更新清单验签。

#### 产物：按信任边界切的威胁表

边界编号即下表 `边界` 列。`response` 只取四值之一，**每个 Accept 必须带理由**。

| # | 边界 | 威胁（STRIDE 类别） | 威胁源 | response | 理由 / 对应的可测需求 |
| --- | --- | --- | --- | --- | --- |

| TH11 | ① socket | 单连接内塞入超大帧耗尽内存（D） | 任何能连上的进程 | **Mitigate** | `MAX_FRAME_BYTES` + 解码器显式拒 `TooLarge`；本轮补了「超大帧被拒」的断言，且用变异测试证明该断言非空泛 |
| TH12 | 全链路 | 握手 token 是源码常量，任何能连上的进程都能算出合法 proof（S） | 另一个本地用户账户 | **Mitigate（两平台）** | 常量已换成每次启动 mint 的 32 字节 CSPRNG（S4），且 2026-11-18 起三条 accept 路径都**双向**验证：任一方自选 challenge 的时代结束了（§19 #1）。可测需求 = 用错的 token 连接必须失败（`session.rs` 的 auth 那条已钉），加一条「不应答 challenge 必须被拒」 |
| TH13 | ① socket（仅 Windows） | 对等身份闸门整体 fail-open：平台说不出对等方时**接受**而非拒绝（S） | 另一个本地用户账户 / 匿名账户 | **Accept** | `studio-host.rs:657-665` 的拒绝分支门在 `else if cfg!(unix)` 上，Windows 上 `peer_uid` 返回 `None` 且 `cfg!(unix)` 为假，于是整条被跳过。注释写的是「未知对等方不被信任」，代码做的相反。**这不是 TH3 的另一半**：TH3 是 DACL（谁能连上），TH13 是连上之后谁能驱动。修它需要 unsafe FFI 取 SID，而专家查证确认没有安全且维护中的依赖可用（§20），所以这是三个选项的决策，不是代码大小问题。**已存在的补偿控制**：#1 落地后，不知 token 的进程再也驱动不了 daemon——认证有了，授权（你是哪个用户）仍然没有。见 §19 #2 |

**这条暴露面有第三条腿，此前没记**：runtime 的 accept 路径（`bridge_server.rs` 的
`serve_connection`）在**两个平台上都没有 peer 闸门**——不调 `peer_uid`，也没有拒绝分支。
Unix 上它被 TH2 的 `0700` 目录兜住（adapter socket 与 daemon 端点同目录，
`lifecycle.rs:177` 建的）；Windows 上它和 daemon 端点一样落在 `\.\pipe\` 全局命名空间里
配默认 DACL，所以 TH13 的暴露对它同样成立。TH1/TH13 原文只写了 daemon 的 surface 腿。 |

**两条不进的**（写下来是为了下次不重复讨论）：TLS on local socket（没有网络路径可打，
攻击者是本地进程，TLS 挡不住它）；握手处速率限制 / 暴力破解锁定（威胁是本地进程而非
分布式猜测，锁定只拖累合法用户）。连接总数与单连接帧大小上限**要**有，但那是资源
耗尽控制，不是反暴力破解。

#### S1 / S2 / S6 的真实卡点不是 B1（2026-11-17 实查）

方案把这三条都记成「卡 B1（没有 Windows 真机）」。逐条查完，**这个归因是错的**——
它们卡在别的地方，而那个地方不需要 Windows 机器就能决定。

**`unsafe_code = "forbid"` 不是障碍，因为已经有先例。** 根 `Cargo.toml:25` 禁 unsafe，
但它是 per-crate 继承的：`studio-bridge` / `studio-host` / `step-studio-runtime`
都写了 `[lints] workspace = true`，所以真的被禁；而 **`peer-uid` 是唯一的例外**
（`[lints.rust] unsafe_code = "allow"`），带着一条注释说明为什么、以及边界在哪：
一次 `getsockopt`，一条 SAFETY 注释。所以「加 unsafe」在这仓里是有成例的，
不是破例。

**S1 的 API 一直都存在，只是没人接。** `miow::pipe::NamedPipeBuilder` 有
`with_security_attributes(*mut SECURITY_ATTRIBUTES)`（`pipe.rs:541`，
`pub unsafe fn`），`create()` 内部就是用 `null_mut()` 调它——也就是
**默认 DACL 是这一行主动选出来的，不是 miow 漏了**。所以 S1 不需要抛开 miow
去裸调 `CreateNamedPipeW`，只需要给 `bind` 传一个显式 DACL。
卡点只剩：那个 `unsafe` 要落在哪个 crate，以及谁批准这个例外。

**S2 卡在语义上，不在机器上。** Windows **有**对等凭据——`GetNamedPipeClientProcessId`——
这点 `peer-uid` 的代码注释此前说反了（写「a named pipe carries no peer credential」），
已修。真正的问题是它回答的是 **pid**，而这个 crate 的教义是「只信 uid 不信 pid」，
理由引的是 unix(7)：pid 记录一次、会回收、进程一改凭据就不再描述对等方。
Microsoft 与 Project Zero 对 `GetNamedPipeClientProcessId` 的警告是同一件事。
把 pid 变成 uid 等价物要 `OpenProcess` → `OpenProcessToken` →
`GetTokenInformation(TokenUser)` → SID，**再多三次 FFI**，而且 `OpenProcess`
要一个调用方未必持有的句柄权限。

所以 S2-Windows 是一个设计选择（pid 闸门 vs SID 闸门），**可以在没有 Windows 的
情况下写**，只是不能在那种情况下验。

**结论**：这三条的「未做」里，没有一条是被缺少 Windows 机器挡住的。
S1 缺的是一次 lint 例外批准；S2 缺的是一个闸门语义决策；S6（DPAPI per-user 范围）
缺的是同一类 FFI 例外。把它们记成「卡 B1」会让下一轮继续以为只能等机器。

### 3.3 明确不做（本地优先桌面应用上的 disproportionate 项）

TLS on local socket（没有网络路径可打，攻击者是本地进程，TLS 挡不住它）·
OWASP Top 10 / ASVS 作为合规计划（XSS/CSRF/SSRF/HTTP 访问控制在此无对应物）·

DREAD 评分（制造虚假精度；排序 + 每条一行理由更诚实）。

## 4. 证据**不**支持的事（单列，防止下次照抄）

1. **「单元测试抓 X%、集成 Y%、E2E Z%」**——找不到任何发布数据。70/20/10 与 80/15/5 是**测试数量**比，

## 7. 新发现：bridge token 是硬编码常量，握手因此不提供身份认证

**高危，且违背方案自己的表述。**

`"step-studio"` 这个 token 是**源码常量**，出现在至少 5 处：

| 位置 | 角色 |
|---|---|
| `apps/desktop-tauri/src-tauri/src/bridge.rs:508` | `pub const BRIDGE_TOKEN: &str = "step-studio"` |
| `crates/studio-host/src/adapter.rs:107,109` | daemon 侧写 token 文件 |
| `crates/studio-bridge/src/client.rs:125,127` | 客户端侧写 token 文件 |
| `crates/studio-bridge/src/transport.rs:146` | Windows 管道名默认值（非 token，同一字面量） |

**方案 `plan.md:419` 写的是「bridge token 只在 daemon 内，经 token-file 注入子进程」。**
一个源码常量不在「daemon 内」——它在二进制里，等于随产品分发给每一个安装。
这正是 OWASP Desktop App Top 10 的 **DA4「reuse of Cryptographic Parameters across all
Installations」**直接点名的形态。

**后果**：HMAC challenge/response 因此只提供**会话绑定**，不提供**身份认证**。
任何能 `connect()` 到端点的本地进程都知道 token，都能算出合法 proof。
按安全简报 F14 的判据，「任何能读到 token 的本地用户/进程即完全通过认证」——
而这里连「读」都不需要，它是公开常量。

**另一个相关事实**：`client.rs:122-128` 的 `token: None` 分支是**写**常量而不是**读**文件。
也就是说 token-file 机制从未被读取过，壳一直是 `token: Some(BRIDGE_TOKEN)` 直接传常量。
**管子在，但没接。**

### 我先前写错了：第 2 条路在 Unix 上**已经建成了**

复查代码时发现 `crates/peer-uid/` 与 `crates/studio-host/src/bin/studio-host.rs:615`：
**每一条被 accept 的连接都过 uid 闸门**，`uid != lifecycle::own_uid()` 即拒绝，
`peer_uid` 读不出来且跑在 Unix 上也拒绝（未知对等方不等于被许可的对等方）。
`crates/studio-host/tests/daemon.rs:744` 钉住同 uid 的正常路径不被误伤。

也就是说在 Unix 上，HMAC **确实已经降级为会话绑定**，对等身份**确实是主授权**。
`"step-studio"` 是常量这件事因此被 uid 闸门兜住：同为 root 或同用户的进程仍然畅通
（这是设计如此，不是缺口——那本来就是「本机本用户」的信任域），
但**另一个本地用户过不来**，方案 `plan.md:419` 的语义在 Unix 上成立。

所以剩下的不是「选 1 还是 1+2」，而是窄得多的一条：

- **S2 在 Unix 上已完成，在 Windows 上不存在。** `peer_uid` 在 Windows 返回 `None`，
  而 `studio-host.rs:620` 的拒绝条件是 `else if cfg!(unix)`——**Windows 上直接放行**。
  于是 Windows 侧只剩常量 token 一道，而它恰好处在 S1（默认 DACL 授 Everyone 读）的
  同一侧：两者叠起来才是 Windows 上的完整暴露面。
- **S4（token 生成与存储加固）在 Unix 上是纵深，在 Windows 上是唯一闸门。**
  优先级因此从「两条路选一条」变成「Windows 侧先补，Unix 侧可选」。

### 已执行：S4（提交 `e0dccb5`）

第 2 条落为代码了。原先记成「留给决策」，理由是「两条路是产品决策」——
那个理由建立在「S2 未实现、要在一和二之间选」的错误认知上。S2 在 Unix 上既然早已建成，
S4 就不再是选择题：硬编码常量严格劣于随机 token，没有可选项。

做法与代价：

- `crates/studio-bridge/src/token.rs`：`generate_token()`（32 字节 OS CSPRNG → hex）
  与 `read_token_file()`。读写都放这一处，壳 / TUI / 测试夹具三处复用。
  `getrandom` 本来就在锁里（`rand_core`、`ed25519-dalek` 都带），**lock 包数 595 → 595**。
- daemon 在 `main` 里 mint 并发布到 `<state_dir>/token`（`0600`），**在 `serve` 绑端口之前**，
  所以端点一可达文件一定在。放在 `bring_up` 里会 race：supervisor 线程 spawn adapter 与
  `serve` 绑端口并发，且每次 adapter 重试都会再 mint 一次。
- `--bridge-token-file` 也指向同一个文件：一个 token、一个写者、两个读者
  （adapter 与壳）。原先它指向 `cwd/.step-studio/token`，那是 per-workspace 的——
  一台机器上的第二个工作区会为同一个 daemon 生成第二份 token 文件。

**过程中修掉的两个 bug**（都不是原先那条 finding，是接线引入的）：

1. `write_token` 把**已经加过后缀的** `state_dir()` 传给一个会再加一次后缀的 helper，
   token 落在 `step-studio/daemon/step-studio/daemon/token`，adapter 起手一个 ENOENT。
   现已拆出 `state_base()` 让根路径只在一处解析。
   `the_daemon_publishes_a_token_where_a_surface_reads_it` 钉住它——把装配改回去，
   该测试转红且消息里带路径。
2. 只做客户端的会话在拿不到 token 时会**自己 mint 一个**并写进一个没人读的文件，
   然后以「challenge proof mismatch」失败——那句话对真实原因（daemon 没发布 token）什么都没说。
   mint 现在归属「谁启动 runtime」；客户端没有 token 就得到
   「no bridge token: the peer published none」。

**测试非空泛已验**：把 `generate_token` 改回常量 → 状态测试转红；
去掉 `0600` 的 `set_permissions` → 转红且消息是「token is 664」。

Windows, so the pipe path could rot unnoticed — **this job is what keeps it honest**」。
它没有保持诚实——daemon 的 Windows 分支**根本编译不过**，而这件事没有任何人发现，
因为门禁红着，而红着的门禁等于没有门禁。

这直接改写了本方案对 Windows 侧的几个判断：

- **S1（DACL）、S2 Windows 侧（`GetNamedPipeClientProcessId`）不只是「卡 B1 没有真机验证」**——
  在 daemon 能编译过 Windows 之前，它们**连写都没法写**。`transport.rs:221` 那段
  `named_pipe::PipeOptions` 绑定代码从未被任何编译器检查过。
- `peer-uid/src/lib.rs` 的 Windows 分支（`peer_uid` 返回 `None`）也从未被编译验证过
  ——它靠的是「签名不点名 `UnixStream` 所以能过」这条论证，不是实证。

**为什么不是一个小补丁**（本轮实证，三条各自独立成立）：

1. `named_pipe 0.4.1` 的 `PipeServer` **不是 `Clone` 也没有 `try_clone`**——
   公开方法只有 `disconnect` / `read_async_owned` / `write_async_owned`。
   `serve_surface` 无 cfg 门地调了 `try_clone` 两次，所以编译不过。
2. `impl io::Read for PipeServer` 与 `impl io::Write for PipeServer`
   **都收 `&mut self`**（源码 `lib.rs:441` 与 `:460`）。所以即便加锁，
   也无法同时持有读者和写者；而**阻塞读会一直攥着锁**，写者将无限期等下去——
   `Mutex` 不是解，是把这个死锁从编译期挪到运行期。
3. `DuplicateHandle` **确实可行**：[Microsoft 原文](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle)
   「The duplicate handle refers to the same object as the original handle」，
   且可以用 `GetCurrentProcess()` 把句柄复制到**同一进程**内。
   但 `named_pipe 0.4.1` **不暴露任何句柄转换**：`PipeServer.handle` 是私有字段，
   全 crate 没有 `AsRawHandle` / `FromRawHandle` / `as_raw_handle` /
   `from_raw_handle`。拿不到 `HANDLE` 就无从复制，也没有构造函数能从副本建出
   第二个 `PipeServer`。

#### 但真正的结论是：**该换的是依赖，不是改写 surface 路径**

上面三条断的都是 `named_pipe 0.4.1` 这个 crate 的 API，不是 Windows 本身。
联网查证后（[crates.io API](https://crates.io/api/v1/crates/named_pipe)、
GitHub `blackbeam/named_pipe`、`mio-named-pipes` 源码直取）：

| 事实 | 出处 |
| --- | --- |
| `named_pipe` 0.4.1（2019-04-06）**是最后一个版本，再无发布** | crates.io `versions[]`，`newest == max_stable == 0.4.1` |
| 上游仓库 **`archived: true`**，最后推送 2019-04-07，**5 个开放 issue + 1 个开放 PR 从未合并**，38 stars | `gh api repos/blackbeam/named_pipe` |
| `mio-named-pipes` 0.1.7（2020-06-30，648 万下载）**实现了 `impl<'a> Read for &'a NamedPipe`（`lib.rs:290`）与 `impl<'a> Write for &'a NamedPipe`（`:341`）**——读写都在**共享引用**上，于是 `Arc<NamedPipe>` 就能给出「读线程 + 写线程」，正是 `serve_surface` 已有的形状 | 源码直取 |
| 同一 crate 还实现 `AsRawHandle`（`:420`）与 `FromRawHandle`（`:426`）——`DuplicateHandle` 那条路随之可达 | 源码直取 |
| 其运行时依赖全是 `[target."cfg(windows)".dependencies]`：`log` / `mio 0.6.5` / `miow` / `winapi`——**Unix 构建零成本**，与本仓已用于 `named_pipe` 的同一模式 | `Cargo.toml` |

**所以方案从「按 `wait(&[T])` 单线程重写 surface 路径」变成「换掉那个 Windows-only 依赖」**，
而后者的 diff 可能小得多：`serve_surface` 的两个 `try_clone` 换成 `Arc<NamedPipe>` 的两个
克隆即可，读写双线程的结构不用动。

### F14 的出处已补：本地 IPC 对等认证的权威说法，以及它自己的两条限制

先前安全简报 F14 自注「这是我的分析，不是引用」。本轮补齐权威出处，
结论是**方向对，但有两处必须写进设计否则会照抄错**：

| 事实 | 出处 |
| --- | --- |
| `SO_PEERCRED` 经 `getsockopt` 在 **`SOL_SOCKET`** 层读取（不是 `AF_UNIX` 层，历史遗留），返回 `struct ucred { pid, uid, gid }` | man7 [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html) / [socket(7)](https://man7.org/linux/man-pages/man7/socket.7.html) |
| **只反映 `connect()` / `listen()` / `socketpair()` 那一刻的状态**；对等方之后降权或改 uid **不反映** | 同上 |
| 单靠 `pid` 做认证不可靠（PID 会复用，对等方可能已换凭据）；健壮做法是配 `SCM_RIGHTS` 传 fd 或 `SO_PEERSEC` / LSM 标签 | 同上 |
| `std::os::unix::net::UCred` 仍是 **unstable**（`peer_credentials_unix_socket`，[rust-lang/rust#42839](https://github.com/rust-lang/rust/issues/42839)），且 `pid` 是 `Option<pid_t>` | [std 文档](https://doc.rust-lang.org/std/os/unix/net/struct.UCred.html) |
| `GetNamedPipeClientProcessId` 确实存在，但 Microsoft 与 Project Zero 都警告：**PID 复用与句柄复制使它单独做授权决策是危险的** | [Microsoft Learn](https://learn.microsoft.com/en-us/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid)、[Project Zero](https://googleprojectzero.blogspot.com/) |

两条限制对设计的实际影响：

1. **uid 可以当主授权，pid 不行。** 本仓 `peer-uid` 恰好只取 `uid` 并丢弃 `pid`——
   这个取舍是对的，但它是**碰对的**，不是论证过的（crate 里 `pid` 字段连读都没读）。
   应当把「为什么只信 uid」写成注释，否则下一个人很容易「顺手把 pid 也拿来用」。
2. **快照语义**：凭据是连接建立时拍的。对本场景（壳连本机 daemon，连完就握手）
   没有实际影响，但它是「不能据此做持续授权」的理由，值得记一句。

**顺带一个事实错误**：`peer-uid/src/lib.rs:6` 写「a named pipe on Windows has no
equivalent at all」。这是错的——`GetNamedPipeClientProcessId` 就是那个 equivalent。
这句错话正是 Windows 侧直接放行的理由，所以它不是文档笔误，是**决策依据错了**。

### 顺带：S1（Windows 管道 DACL）仍卡 B1，且它是三道里的一道

`transport.rs:221` 的 Windows 绑定是 `named_pipe::PipeOptions::new(endpoint).single().and_then(|c| c.wait())`
——**没有传 `SECURITY_ATTRIBUTES`**，`named_pipe 0.4.1` 整个 crate 里也搜不到这个符号。
Microsoft 文档明写 `CreateNamedPipe` 传 `NULL` 安全描述符时，默认 DACL
「授予 Everyone 组和匿名账户读取访问权」，OWASP DA6 直接点名「Misconfigured Named-Pipes」。

**这不是我们选的，是 crate 默认值。** S4 落地后（提交 `e0dccb5`）token 那一层在全平台都关了，
Windows 侧剩两道：DACL 不限制（S1）、没有对等身份闸门（S2 只做在 Unix 上）。

### S9 已执行：更新签名对照 TUF 审完，答案比预想的靠前

S9 原本只写了「审一遍」加三个待答问题。逐行读 `packages/runtime-installer/src/update-manifest.ts`
（验签本体）、`update-index.ts`（水位线）、`crates/studio-host/src/signing.rs`（Rust 侧那份）
之后，三个问题都有答案，**但真正的发现不在 TUF 缺口上**。

#### TS 侧的验签器是好的，而且比方案以为的更接近 TUF

| TUF 概念 | 本仓实现 | 证据 |
| --- | --- | --- |
| 角色 / 多钥 | `keyId` + 调用方传入的 keys 映射，`keyId` 不在表里直接拒 | `update-manifest.ts:77` |
| 规范编码 | 递归排序键 + 域名分隔前缀 `omp-studio-update-v2\n`，签名覆盖的是**原始字节**而非重新序列化的对象 | `canonicalUpdateJson` / `updateSigningBytes`，34-36 行 |
| 水位线（防回滚） | `index.sequence < lastSequence` 即拒，且有本地 watermark 概念 | `update-index.ts:437` |
| 未知字段 | 重新规范化后与原文逐字节比对，多一个字段就拒 | `update-manifest.ts:95` |
| 失败方向 | keys 表默认 `{}`，空表意味着**每一份签名清单都被拒** | `installer.ts:84` |

「泄了签名钥能否吊销」——**能轮换，不能即时吊销**：keys 是映射所以可以换钥，
但映射由调用方给，而本仓没有任何生产调用方传它（见下），所以现实是
「泄钥 = 换构建」。「旧清单能否被重放」——**不能，水位线挡着**，
这是本轮最实在的一条：`sequence` + watermark 正是 TUF 的 rollback protection，
不需要引 TUF 就已经有了。

#### 但真正的问题：这份好的验签器没有生产调用方，另有一份更弱的在旁边

1. **`crates/studio-host/src/signing.rs` 无任何生产调用方。** 全仓 grep 只命中
   `lib.rs:17` 的 `pub mod signing;` 和 `tests/daemon.rs:934,1016` 两处**注释**
   （后者写「`signing` 已经覆盖了降级拒绝」，把验收条件 defer 给了它）。
   `verify` / `sign` / `check_digest` 只被自己的单测调用。
2. **它比 TS 那份弱，且弱在安全模型上**：无 `keyId`、无 sequence 水位线、
   无未知字段拒绝。若有人照着它接「签名更新」，拿到的是更差的那套。
   **原先还有一把 bake 进二进制的全零 `VERIFYING_KEY_BYTES`，本轮删掉了**：
   全零 ed25519 验签钥可以被 `SigningKey::from_bytes(&[0u8; 32])` 匹配，
   谁都算得出来，而那个常量**全仓零引用**——第一个把它接上的人，会发布一个
   「什么签名都验得过」的检查。这正是 bridge token 硬编码常量的同一个形状，
   只不过那回真的接上了。
3. **`fetchUpdateIndex` 也没有生产调用方**——它是全仓唯一强制执行 watermark 的函数，
   而 `lastSequence` 这个参数在 `apps/` 与 `packages/*/src` 里**无人传入**。
   也就是说防回滚的水位线写了、测了，但没接到任何会跑它代码的路径上。

`m5.md` 把 M5.2 ed25519 更新记为「🟡 部分：signing + update-index 在，更新流程未接」——
这个判断是对的，但「未接」的程度比它听起来更彻底：**两份实现都没接**，
而没接的那一份（TS）恰恰是应该接的那一份。

**已执行（补缺失的测试）**：`signing.rs` **不能删**——它握着「降级被拒」这个属性**唯一**的
测试，而 TS 侧（真正该接的那份）一条都没有。`fetchUpdateIndex` 是全仓唯一强制执行
watermark 的函数，此前零测试。新增 `packages/runtime-installer/test/update-index.test.ts`
三条：等于水位线放行（重查同一个版本必须仍可能）、低于水位线拒绝（**签名合法、格式正确，
仍然拒绝**——这正是回滚攻击）、payload 与签名 digest 不符拒绝。已注册进
`scripts/core-suites.mjs`，并验过非空泛：删掉 watermark 检查，`npm run check --only
runtime-installer` 转红。

**已执行（拆掉诱饵）**：删掉 `VERIFYING_KEY_BYTES` 常量本身。它是 `pub`、
文档写着「等真钥 mint 出来再 bake」，而没有任何 build script 在 bake，
也没有任何引用——一个等着被信任的占位符。删掉它不影响任何测试（它们各自 mint 钥对），
`cargo test --workspace` 365 passed 不变。

**仍待决**：`signing.rs` 这个模块删还是降级。测试迁移的顾虑已经解除（TS 侧本轮补了
三条 watermark 测试，且验过非空泛），剩下的理由只剩一条：**它是更弱实现的诱饵**。
倾向删——它无生产调用方、`ed25519-dalek` 全仓只服务它一个、而更新流程真要落在 Rust
时，重新写一个会比继承一个「钥匙问题已经被人拆掉、模型问题还在」的模块更安全。
但这是删别人 271 行，留给项目负责人点头。
另记一处潜在而非可利用的坏味道：`signing_bytes` 用 `unwrap_or_default()`，
序列化失败会退化成对空字节签名与验签（`Manifest` 是纯 String/u64，现实里不会触发）。

### 专家团审评 `6285654`：三条独立印证同一个 bug，另翻出一个我顺手修掉的漏洞

依赖替换落成后，派了三个只读审评 agent 并行复核（Rust 系统正确性 / 安全 / 范围与海拔）。
三个都独立命中同一条，另外安全那条翻出一件我完全意料之外的事。

#### 1 · `FILE_FLAG_FIRST_PIPE_INSTANCE`：rebind 一直是死的（三个 agent 互相印证）

`miow::pipe::NamedPipe::new` 走 `NamedPipeBuilder::new`，其 `dwOpenMode` 硬编码
`PIPE_ACCESS_DUPLEX | FILE_FLAG_FIRST_PIPE_INSTANCE | FILE_FLAG_OVERLAPPED`
（`pipe.rs:468`）。Microsoft：设了该标志后「创建第一个实例成功，创建下一个实例失败并返回
ERROR_ACCESS_DENIED」。miow 自己的测试 `named_not_first`（`pipe.rs:597-603`）正是断言这件事，
并演示 `NamedPipeBuilder::new(&name).first(false).create()` 是官方解法。

两个 serve 循环都在把连接交出去**之前**重新 bind（`bin/studio-host.rs:602`、
`bridge_server.rs:168`），而上一个实例仍被持有 → 第二次 `CreateNamedPipeW` 必然
ERROR_ACCESS_DENIED → 打印 `rebind failed` 并 `return` → **daemon 服务完一个 surface 就退出**。

**不是本轮引入的**：`named_pipe 0.4.1` 的 `single()` → `multiple(1)` → `create_named_pipe(first: true)`，
同一个标志（`lib.rs:256-259`，`first` 默认 true）。旧代码一样坏。
**但本轮新增的注释断言了相反的事实**，那是我引入的。

**已修**：`bind` 改用 `NamedPipeBuilder::new(endpoint).first(false).max_instances(1).create()`。
两个 serve 循环上那段「为什么」的注释一并补上。

#### 2 · `nMaxInstances` 1 → 255，是被我的修复激活的

`named_pipe` 的 `multiple(1)` 给 `nMaxInstances = 1`；miow 的 builder 默认
`PIPE_UNLIMITED_INSTANCES`（255）。这个默认在 `first(true)` 之下是惰性的，
**我一清 flag 它就变活了**——255 个同名管道实例，而 `serve_surface` 是刻意
「一次一个 surface」的。没人选过 255，是 builder 默认值静默穿过了替换。

**已修**：显式 `max_instances(1)`。

#### 3 · 我顺手修掉了一个真漏洞（安全审评发现，我已逐条核实）

`STEP_STUDIO_TRANSPORT_ENDPOINT` 这个环境变量在改动前有**两个读取方、零个写入方**：

```
6285654^:crates/step-studio-runtime/src/bridge_server.rs:1271
6285654^:crates/studio-bridge/src/client.rs:552
```

没有任何代码设置它。于是 `env::var(..).unwrap_or_default()` 给出 `""`，
`endpoint_for_bind("")` 的回退是硬编码 `"step-studio"`（原 `transport.rs:146`）→
读取方去连 `\\.\pipe\step-studio`。

而 daemon 实际绑的是 `default_endpoint()` = `step-studio-{uid}`，Windows 上 `own_uid()`
恒为 `0`，即 `\\.\pipe\step-studio-0`——**一个不同的、且与产品无关的名字**。

后果：任何本地进程预先创建 `\\.\pipe\step-studio`，adapter 的 reader 线程就会作为
**客户端**连上它并从那里读帧，帧经 `host_tx` 进 adapter 事件泵再到壳。
**等于完整的协议注入——伪造回执、伪造 CLI 输出。** 且该值来自进程环境，
可被 adapter 继承。客户端侧（`client.rs:552` 的 `stream_clone`）同一回事。

这个漏洞随 `reopen` 与环境变量一起被删掉而消失——**我在删它时并不知道它在堵这个洞**。
审评 agent 是从「删除是否移除了安全相关行为」这个角度反向查出来的。

#### 4 · 审评退休了我最大的两个担忧

- **客户端句柄不是 overlapped**：`miow::pipe::connect` 用 `OpenOptions` 打开，
  Rust std 的 Windows `OpenOptions` 不设 `FILE_FLAG_OVERLAPPED`，所以 `File::read/write`
  是在同步句柄上带 NULL `OVERLAPPED` 的 `ReadFile`/`WriteFile`——正确的阻塞路径。
  我原担心「同步 I/O 打在 overlapped 句柄上」不成立。
- **线程局部 `OVERLAPPED` 正是共享安全的原因**：`with_threadlocal_overlapped` 用
  `thread_local!` 存 `RefCell<Option<Overlapped>>`，读者与写者各拿自己的一份，
  不共享状态、不串行化。且它跨整个 I/O 持有 `borrow_mut`，将来若有重入会 panic 而非静默损坏。

另确认：`PipeHandle` 的转发对实际用法完备（`next_frame`/`read_frame` 只要 `read`，
`write_frame` 只要 `write_all` + `flush`）；diff 无夹带。

#### 7 · 联网核实 `DisconnectNamedPipe`：我注释里的机制写错了，顺带查出一个静默行为差异

[Microsoft 原文](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe)：
「the client **receives an error** the next time it attempts to access the pipe」——
是**错误**，不是我注释里写的 EOF。另有一条：「any unread data in the pipe is
discarded」，要保证不丢数据得先 `FlushFileBuffers`。

**功能上仍然成立**：壳侧 `spawn_reader` 对 `Ok(None)` 与 `Err` 的处理**完全相同**
（都 `shared.close()` 后返回），daemon 的 relay 循环与 runtime 的 pump 同样把读错误
当作关闭。所以对端照样会注意到，只是机制是错误而非 EOF。注释已改正。

**但同一次核实翻出一个静默的行为差异**：`named_pipe 0.4.1` 在两个 `Read`/`Write`
实现里把 `ERROR_BROKEN_PIPE` 规范化成 `Ok(0)`（`lib.rs:450`、`:1029`）——
**`miow` 没有这个翻译**。于是原来看到干净 EOF 的 reader，现在看到错误。

三个 reader 全都走错误分支（已逐个确认），所以现在没有 bug——但这个处理**过去是兜底，
现在成了正常断开的必经路径**。后来任何只匹配 `Ok(None)` 的代码都会静默漏掉关闭的管道。
这一点已写进 `transport.rs` 的注释。

### 9 · Windows 上 daemon **无法干净退出**（新发现，本轮最高优先的未修项）

追查「Windows 运行期到底还差什么」时发现的，比此前记录的所有 Windows 项都严重。

`serve` 在**主线程**直接调用（`bin/studio-host.rs:226`），`shutdown` 在它返回**之后**
才执行（`:228`）。Windows 臂的循环是：

```rust
loop {
    if daemon.stopping.load(Ordering::Relaxed) { return; }   // 只在这里检查
    let connection = transport::accept(listener)?;           // ConnectNamedPipe，无超时，永久阻塞
    ...
}
```

`transport::accept` 在 Windows 上是 `ConnectNamedPipe`，**没有超时变体**；
`stopping` 只在进入阻塞**之前**检查一次。Unix 臂正是为这个才把 listener 设成
non-blocking，它的注释（`:541-543`）写明了失败形状——Windows 臂没有对应物。

**后果**：`stopping` 一旦在阻塞期间被置位（`watch` 的 grace-clock 排空，或升级标记），
循环永不重新检查 → `serve` 不返回 → 主线程的 `shutdown` 不执行 → **进程不退出**。
而因为本轮让 `bind` 立即返回，daemon 的**整个空闲生命周期**都停在这个阻塞里，
不是边角情况。grace-clock 排空（「N 次启动失败且无 surface 就退出」）在 Windows 上
**永远不会触发**。

**已落码：上面两条之外的第三条出路**（`transport::wait_or_stop` + `accept_until`）

把阻塞调用丢到线程上跑，本线程用 `recv_timeout(50ms)` 轮询，每次醒来重读
`stopping`。三条路里只有它同时满足：不动进程生命周期语义（`serve` 仍在主线程、
`shutdown` 仍在它之后）、不要求 `ConnectNamedPipe` 有超时变体（它没有）、
并且**平台无关**——只有 `accept_until` 那一个 Windows 壳子按平台分叉，
轮询 / 标志 / 通道那部分在 Linux 上就被测试覆盖。

被放弃的那个线程由「进程退出时 `main` 返回，卡在 syscall 里的线程不拦着进程结束」
正当化，这句话写进了 `wait_or_stop` 的文档注释。

三条测试钉住它。第三条是**变异验证过的**：把 `if stop.load(...)` 改成
`if false && stop.load(...)`，测试挂死到超时——不是失败，是挂死——
说明它不是空泛的。它自己也写错过一次：`stop.store(true)` 放在 `wait_or_stop`
返回**之后**，而它正因没人置位才不返回，于是死锁；改成由另一个线程在 100 ms 后
置位才成立。

**仍然卡 B1**：真机上 daemon 确实能退出、grace-clock 排空确实会触发。
`wait_or_stop` 的正确性只证明「标志被读到了」，证明不了「进程真的走了」。

#### 怎么修的（以及为什么不只是补门）

| --- | --- |
| `browser_observation` / `prediction` | 整模块 `#[cfg(unix)]`；Windows 臂在新文件 `unsupported.rs`，9 个命令同名同形状，只换答案 |

#### 仍然没做

### 11 · Windows 上**一个测试都没跑过**，于是一个 keystore 静默丢失了全部数据

先说最重的：**Windows 上丢失过用户数据，而每一道门禁都是绿的。**

`apps/desktop-tauri/src-tauri` 的 `OsKeystoreCodec` 把数据加密钥存在 OS keystore 里，
AES-256-GCM 加密 service definition 文件——那个文件的 `env` 块放着用户的 API token。
keyring 3 在 Windows 上**默认不用 Windows Credential Manager**：没有
`windows-native` feature 时，`keyring/src/lib.rs:296` 把默认 store 设成
**`mock`**——一个进程内的 `Mutex<RefCell<MockData>>`，
`CredentialPersistence::EntryOnly`，而且每个 `Entry::new` 建一个全新的
（`mock.rs:217`：「Since mocks don't persist between sessions, all mocks start
off without passwords」）。

后果链，每一环都"正常工作"：

1. 首次启动：`get_password()` → `NoEntry` → `data_key()` mint 一把 32 字节钥，
   `set_password()` 成功（写进那个进程内 map）。**加密正常，用户无感。**
2. 下次启动：新进程、新 map → `NoEntry` → **mint 第二把钥**。
3. 磁盘上每一个用旧钥加密的 service definition，从此解不开了。

而这个模块的**第一条规则**写的就是：「keystore 够不着时绝不绕过去，新 mint 一把钥
会让盘上所有定义解不开且看起来像成功」。mock 击败它的方式是**回答"够得着"**：
`Entry::new` 返回 Ok，`get_password` 返回 `NoEntry`——正是
`available()` 认定"有 keystore"的那个组合（`service_definitions.rs:113-115`）。

**修**：Cargo.toml 的 keyring features 加 `windows-native`。lock 从 595 → 605 包，
新增的 10 个全是 Windows import shim（`windows-sys` 0.60 与已有的 0.61.2 不合并，
因为 `^0.60` 不含 0.61）。代价可忽略，对面是静默丢数据。

#### 为什么每一道门禁都是绿的

CI 的 Windows job（`.github/workflows/ci.yml` 的 `rust-windows`）**只跑 clippy**，
不跑 `cargo test`。注释写的理由是「运行时未验证：没装 Step CLI，e2e 会 skip；
GUI 壳不能在 hosted runner 上跑」——两句都对，**但两句都不覆盖单元测试**。
而唯一能抓住这个 bug 的测试（`the_real_codec_answers_consistently_about_the_keystore`）
只在 **Linux** 上跑，那台机器上没跑 Secret Service，于是它走 `else` 分支、
**什么都不断言**。

所以 §11 原标题「25 个测试不存在」还说得太轻了：不是 25 个缺席，
是 **Windows 上一个测试都没执行过**。25 个是静态数出来的缺席者；
真正的问题是执行数为零。

#### 补的测试，以及它为什么抓得到

已有的那条一致性测试**抓不到**：在 mock 上 `available()` 真、`data_key()` 真成功、
同进程内 encrypt/decrypt 往返也真成功——它全绿。缺的断言是**持久性**：
写进去的钥，一个**全新的 `Entry`** 必须读得出来。真实的 store 按
(service, user) 查，mock 只认建它时那个 entry。

#### `daemon.rs` 的门比它看上去的松

真正逼着 `#![cfg(unix)]` 的只有两处 `UnixStream::connect(&endpoint).is_ok()` 探针
（`:250`、`:1126`）。文件里对 mode 的检查**本来就已单独 `#[cfg(unix)]`**

2. 状态目录：测试设 `XDG_STATE_HOME`，而 Windows 的 daemon 读 `LOCALAPPDATA`

换句话说：Windows 上唯一那道闸门，它的权限属性是零测试。
Unix 上有，Windows 上没有，而 Windows 恰是那道闸门更弱的地方。

## 12. 联网查证：Windows 命名管道的权威说法（2026-11-17）

前面几节的证据此前有一部分是凭记忆写的。逐条回到 Microsoft 文档核对，
**两条对、一条我自己写错、一条查不到出处所以不作数**。

### 核对为真（Microsoft 原文）

**默认 DACL 授 Everyone 读。** [`CreateNamedPipe` 的 `lpSecurityAttributes`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea)
与[《Named Pipe Security and Access Rights》](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)
两处同文：

> If _lpSecurityAttributes_ is **NULL**, the named pipe gets a default security
> descriptor. The ACLs in the default security descriptor for a named pipe grant
> full control to the LocalSystem account, administrators, and the creator owner.
> They also grant **read access to members of the Everyone group and the
> anonymous account**.

S1 的证据成立。注意它说的是**读**权限——本地任何用户都能连上并读帧，这正好覆盖
`studio-bridge` 在 Windows 上中继的全部内容。

**`FILE_FLAG_FIRST_PIPE_INSTANCE` 会让第二个实例失败。**

> If you attempt to create multiple instances of a pipe with this flag, creation
> of the first instance succeeds, but creation of the next instance fails with
> **ERROR_ACCESS_DENIED**.

§7 那条（daemon 只能服务一个 surface）成立。

**`nMaxInstances` 上界是 255，超了直接报错。**

> Acceptable values are in the range 1 through **PIPE_UNLIMITED_INSTANCES** (255).
> If _nMaxInstances_ is greater than PIPE_UNLIMITED_INSTANCES, the return value is
> **INVALID_HANDLE_VALUE** and GetLastError returns **ERROR_INVALID_PARAMETER**.

所以把它钉回 1 不只是"别过度授予"，也是唯一不会踩到这个上界的值。

### 方案里那条自己写的断言，这次算出来了

S1 写「避免 `FILE_GENERIC_WRITE`（它与 `FILE_CREATE_PIPE_INSTANCE` 共享取值，
会顺带授予创建管道实例的权限）」——这句**是对的**，而且能从同一张表算出来：

| 常量 | 值 |
| --- | --- |
| `FILE_FLAG_FIRST_PIPE_INSTANCE` | `0x00080000` |
| `WRITE_OWNER` | `0x00080000` |
| `FILE_GENERIC_WRITE` 含 `WRITE_OWNER` | 是 |

也就是说，给管道 DACL 授 `FILE_GENERIC_WRITE`，会连 `WRITE_OWNER` 一起授出去，
而 `WRITE_OWNER` 与 `FILE_FLAG_FIRST_PIPE_INSTANCE` **是同一个位**。授的是写权限，
拿到的是"再建一个实例"和"改 owner"。这条此前只是断言，现在有推导。

### 我自己写错的那条

方案此前写：三个功能的读超时，「`transport::wait_or_stop`（本轮刚落码）正是那个形状」。
**错的。** [《Named Pipe Type, Read, and Wait Modes》](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-type-read-and-wait-modes)：

> The nonblocking-wait mode is supported for compatibility with Microsoft LAN
> Manager version 2.0. **This mode should not be used to achieve overlapped input
> and output (I/O) with named pipes.** Overlapped I/O should be used.

同页确认阻塞等待确实没有超时：

> In blocking-wait mode, the functions **wait indefinitely** for a process on the
> other end of the pipe to complete an operation.

所以有界等待的正解是 `FILE_FLAG_OVERLAPPED` 开管道 + `WaitForSingleObject` 带超时 +
超时后 `CancelIoEx`，不是"丢到线程上轮询"。线程加轮询能解决的是"调用方想在中途放弃"，
解决不了"这次读本身要有截止时间"——后者才是三个功能需要的（它们要靠读超时判断
runtime 是不是还在）。

**范围核对**：`wait_or_stop` 在本仓只被 `accept_until` 用，而被放弃的那次调用是
listener 上的 `ConnectNamedPipe`，且 `serve` 循环在 accept 成功后**立刻重新 bind**
（`studio-host.rs:615`），旧 listener 随即被 drop。所以它不碰读超时这个问题，
§7 那个修复本身仍然成立——只是不该被推广成读超时的解法。

### 查不到出处，所以不作数

检索中出现一条说法：「同步管道操作是串行的，同一句柄上并发的 `WriteFile` 会阻塞到
挂起的同步 `ReadFile` 完成」。**这条没有拿到 Microsoft 出处**（检索超时，
工具明确返回"no sourced content to cite"）。它听起来符合 Win32 的常识，
但本轮的纪律是不把没出处的东西写进证据列——所以记在这里，标为**未证实**，
宁可它被后人重新查一遍，也不要它以一个引用过的样子流传下去。

## 14. 联网查证：Windows 对等身份，Project Zero 的结论（2026-11-17）

S2 此前写「Microsoft 与 Project Zero 对 `GetNamedPipeClientProcessId` 的警告是同一件事」——
**那句话没有出处**。这次查到了，出处是 James Forshaw 在 Google Project Zero 的
《Windows Exploitation Tricks: Spoofing Named Pipe Client PID》（2019-09-25）。

### 作者的结论句，逐字

> Even in the absence of the ability to arbitrarily spoof the PID value it should be
> clear that this PID should not be relied upon to make security decisions as it
> doesn't necessarily reflect the actual client, **just the process which opened the
> pipe**.

开篇 also states the purpose plainly:

> As relying on this PID is dangerous I decided I should highlight ways of spoofing
> the PID value so that developers can **stop using it as an enforcement mechanism**

### 三条具体手段

1. **PID 回收**。NPFS 在**建立连接时**记下 PID，不是每次请求。
   Forshaw 指出：检查若紧跟连接就来不及回收，**但若检查发生在客户端首次读写之后，
   就可以拖到 PID 被回收**。他列的优势之一是「Possible to create multiple pipes
   with different PIDs to maximize the chances of PID recycling」。
2. **经本地 SMB 连接**。EA buffer 为空时用当前进程 PID，而 SMB server 跑在 System 里，
   于是客户端 PID 被设成 **4**；若能自己实现 SMB2 协议，则可以**任意指定 PID**。
   （前提是能访问本地 SMB，沙箱内不可用；且仅 1709 及以上。）
3. 相关的 access-mode mismatch bug class：内核态请求可以注入自定义 EA buffer 同时伪造
   client PID 与 session ID；用户态被内核的模式检查挡住。

### 这对本仓意味着什么

**S2 的"pid 闸门 vs SID 闸门"二选一，有了确定答案：pid 闸门不可以。**
不是"更弱"，是作者明确说不要用它做执行机制。所以 Windows 侧唯一可做的对等身份是
`OpenProcess` → `OpenProcessToken` → `GetTokenInformation(TokenUser)` → SID——
也就是更贵的那条路，没有便宜选项。

**还有一条直接约束我们的设计**：PID 记录在**连接时**，所以任何对等检查必须发生在
**accept 的那一刻**，不能延后到首个请求。将来若有人按"每请求校验对等身份"来实现，
正好落进 Forshaw 描述的可回收窗口。这一条已写进 §5 的 S2 条目。

另记：`transport::wait_or_stop` 这轮被审评指出「同步管道操作串行」的说法无出处，
我标为未证实（§12）；现在从 miow 0.3.7 源码确认它内部对 `Read`/`Write for &NamedPipe`
用的是 **overlapped** I/O（线程局部 `OVERLAPPED`，句柄以 `FILE_FLAG_OVERLAPPED` 打开），
所以那条说法对本仓不适用——但 Project Zero 这篇与它无关，是另一个问题。

## 15. T4 应用到 Rust：协议面 9 个可变异，3 个 pseudo-tested，以及两个我自己的假阴性

§0 论证协议边界是最高风险面，而系统性扫描此前只做了渲染层。这一节补上，
范围取 `studio-bridge`（帧编解码 + 握手 + token + 传输），28 个导出函数。

### 方法，以及 Rust 与 TS 的不同

TS 那边一个变异（`return null as unknown as T`）通吃；Rust 必须按返回类型分三类，
**三类的含义不同**：

| 类 | 变异体 | "绿"的含义 |
| --- | --- | --- |
| `default` | `return Default::default();` | 没有测试断言返回值（TS null 的对应物） |
| `err` | `return Err(io::Error::other(..))` / `Err(String::from(..))` | 成功路径无人断言 |
| `noop` | 函数体清空 | **副作用变异**：没有测试断言副作用 |

19 个跳过了，理由是合成不出平凡值：自定义错误类型（`FrameError` / `BridgeError`）
没有无参构造；`Option<io::Result<T>>` 含裸泛型；`impl Read` 与 `&mut Accepted`
无法合成。**跳过的不算进分母**——所以这一节的比例不能与 §2.1d 的 22/65 并列。

### 两个我自己的假阴性，都抓在报告之前

**1. 括号匹配差一位。** `end` 指向 body 的 `}`，我切片时把它留下了，每个变异都多一个
`}`，全部 COMPILE_FAILED。第一轮 28 行结果里 9 个 "COMPILE_FAILED" 全是这个原因，

而那恰恰是本项目最关键的平台差异函数（唯一知道 Unix socket 路径与 Windows 管道名

顺带还有第三个：基线我用 `tail -3` 读，截掉了 lib 那 14 条，把 26 误记成 12。

**这三条合起来是一个教训**：变异扫描的产出是"哪些函数的契约无人断言"，
但扫描器本身会以三种方式说谎（自己的 bug、变异没落地、基线读错）。
不先验证变异真的生效，报出来的就是假发现。

### 那条挂死已修，并且证明过

定位到 `transport::accept` 在 Unix 上无界阻塞：connector 线程早就带着错误返回了，
而没人走到那个会把它打印出来的 `join`。这两条测试自己注释里写了为什么给**读**
加 10 秒超时（`set_read_timeout`，「So a broken `duplicate` fails rather than hangs
the suite」）——accept 有同一个洞，没补。

**修**：`accept_within(listener, 10s)`，建在 crate 自己已经测过的
`wait_or_stop` 上，不写第二份轮询。

**非空泛证明**（同一套坏传输，只改 accept 这一处）：

| | 结果 |
| --- | --- |
| 修复前，无界 accept | **挂死**，45 秒被 kill，从不报告 |
| 修复后，有界 accept | **10.02 秒失败**，`accept: Custom { kind: TimedOut, error: "accept timed out" }` |

所以破坏必须同时动 `endpoint_for_bind`。这本身就是一课：**只破坏要测的那一处，
往往复现不了 bug**。

## 17. 安全审评（第三次才跑成）：7 项发现，以及我一行修法错在哪

前两次派专家都因基础设施故障中断（模型 404、Zed 登录过期 401），第三次换成不钉坏模型的
agent 类型才跑成。它读了代码，7 项里我逐条核实了最具体的三条，**全部逐字为真**。

### 已核实的发现

**1. runtime 丢掉自己的握手验证，令 claim 方可自选 challenge。**（我原称之为「签名预言机」，那不是术语，见 §20。）
`bridge_server.rs:1163`：`let _ = verify_hello(&body, &config.token, challenge); // validation only`。
而它紧接着对**调用方给的任意 challenge** 返回有效 proof
（`:1162`），`instance_id` 是 `step-runtime-<pid>`——pid 可猜。
于是任何对等方选一个 challenge 就能拿到 `HMAC-SHA256(token, challenge, instance_id)`，
即协议唯一秘密的签名预言机。

**2. Windows 上 peer 闸门 fall-through，且与注释相反。**
`bin/studio-host.rs:657-665`：

```rust
if let Some(uid) = peer_uid(&stream) {
    if uid != lifecycle::own_uid() { ...return; }
} else if cfg!(unix) {
    eprintln!("...cannot tell who this surface is; refusing it");
    return;
}
```

上面三行注释写的是「平台说不出对等方是谁，连接被拒绝而不是被信任」。
而 Windows 上 `peer_uid` 返回 `None`（其 `#[cfg(not(unix))]` 臂），`cfg!(unix)` 又为假，
**else-if 整条被跳过，连接被接受**。注释与代码相反，且方向是 fail-open。
配合已确认的 NULL DACL，Windows 上任何本地用户都能走到 surface 路径。

**3. `open_url` 把渲染进程给的字符串交给 `cmd.exe`——已修。**
`chrome.rs` 只查 `https://` 前缀，Windows 上跑 `cmd /C start "" <url>`。
Rust 的 `Command` 在 Windows 上**只在参数含空格或引号时才加引号**，
所以 `https://x&calc`（无空格）原样到达 cmd，`&` 被 cmd 当命令分隔符解析。
而 `preload.ts` 明写 Tauri ACL 不是信任边界、页面脚本能到
`window.__TAURI_INTERNALS__`——这是一次渲染进程沦陷换命令执行。

**修法**：`raw_arg`（`std::os::windows::process::CommandExt`，**安全方法**，
不需要破 `unsafe_code = "forbid"`）绕过 Rust 的引号逻辑，自己给 URL 包上引号，
cmd 就把它当一个 token。另加一条拒绝：URL 含 `"` 直接拒——引号会突破那层引号，
而 URL 里本来不该有它。**不是字符黑名单**：`&` 在查询串里合法，所以修法必须是
结构性的（引号）而不是禁用字符。

两条测试，引号那条**变异验证过**（删掉守卫即转红）。

**过程中被 Linux 门禁抓到一个错**：我最初把 Windows 臂写在
`else if cfg!(target_os = "windows")` 里。`cfg!` 是**运行时布尔**，不是编译期门——
臂里的代码在 Linux 上照样编译，于是 `std::os::windows` 与 `raw_arg`
（只存在于 Windows 扩展 trait）在 Linux 上直接编译失败。改成 `#[cfg]` 真门才对。
这和本轮反复出现的病同源：**看起来门住了，其实没有**。

### 我尝试修第 1 项，错在哪

我把 `let _ =` 改成 `verify_hello(...)?`。**e2e 立刻全红**：
`adapter closed before hello`。失败方式说明了真实结构：

daemon 发来的 hello 是**请求**（`adapter.rs:230-238`：有 `challenge`，**没有
`challengeProof`**），而 runtime 把它当**响应**去验——`verify_hello` 要求
`challengeProof`，所以在这一腿上它**永远不可能成功**。

所以 `let _ =` 不是懒惰，是在掩盖一个调用错误。而真实形状比"验证被丢掉了"更准：

**这一腿的认证是单向的。** daemon 发 challenge、验 runtime 的 proof（`adapter.rs:247`）；
runtime 答任意 challenge，但**不验 daemon**。方向反了，正是审评说的"要反转 challenge"。
这是一次**双方协议变更**，不是一行能修完的。已回滚，e2e 复跑 15 条全绿。

这一条也修正了 §13 我自己的一个说法：我在那儿写"challenge 现在每次连接随机"——
对，但只对**挑战方也是验证方**的那两腿成立。surface 这一腿上 challenge 由调用方选，
新鲜度是装饰性的。

### 其余四项（审评所报，我未逐行核实）

4. **Windows 管道名来自 `USERNAME.len()`**（`lifecycle.rs:80-87` →
   `default_endpoint()` → `step-studio-<len>`）。`\.\pipe\` 是机器级单一命名空间，
   所以**同长度用户名共享同一个 daemon 名**，且攻击者可以故意选一个撞名的用户名。
   `ponytail:` 注释说"Windows 上是同一个数字"，说得太轻：那是个长度，不是常量。
   影响：叠加发现 1/2，可跨用户够到一个不认证的 daemon；以及预绑定名字的 DoS。
5. **接受侧读取无超时 → 本地 DoS。** `set_read_timeout` 在 Windows 上被接受但忽略
   （`transport.rs:283-293` 自己写了），且没有调用方给**已接受**的连接设超时。
   daemon 一次只服务一个 surface，任何进程连上发 0 字节就把唯一槽位永久占住。
6. 同上的 `client.rs:183`：`:159` 设的 300 秒超时在 Windows 上被静默丢弃。
7. **token 的 0600 只对一个 writer 成立——已修，而且比审评说的重。**
   三处 mint：`state.rs:199` 写了 chmod，`adapter.rs:116` 与 `client.rs:140`
   用裸 `fs::write`。`client.rs` 那条是**新 mint** 路径，文件若不存在就是
   umask 默认。

   审评判断"当前不可利用"——**这句在这台机器上不成立**：umask 是 `002`，
   破坏验证时去掉 chmod，token 落成 **664，组可写**，不只是全局可读。
   同组任何本地用户可读到一个 256 位会话秘密，而它保护的正是 HMAC 握手的
   会话绑定。审评的推理链没错（"daemon 路径上文件已存在所以模式保留"），
   只是漏了 mint 路径本身会新建文件。

   **修**：`token::write_token_file`（写 + chmod 0600）收口到模块自己的文件，
   三个 mint 点全走它；模块文档原来无条件声称 0600，现在这句话才成立。
   一条 `#[cfg(unix)]` 测试，**变异验证过**：去掉 chmod → `token is 664` 转红。

### 审评认为没问题的（对我有参考价值）

`packages/runtime-installer` 的验签与安装链它读了，评价是 well-built：
Ed25519 over `manifest \0 checksums`、全文件覆盖且拒符号链接、
staging 与 activation 双重复验、原子 `current.json`、激活前 self-check。
它明确说**没读**传输层（`remote-environment.ts` / `update-manifest.ts`），
所以"artifact 是否走固定 TLS 通道、是否跟随重定向、`trustedKeys` 是否可能来自网络"
仍是空白——这是它建议的下一处。

渲染层它查了几个 sink 都正确：mermaid 三处皆 `securityLevel: "strict"`、
`editorDom.ts` 转义了 `& < > "`、`brands.tsx` 注入的是编译期常量。
它也没审计 markdown 渲染器的 link/href 处理。

### 已核实、未修（5），以及未修的理由

**#1 daemon 不验 surface（原表述「runtime 签名预言机」，见 §20 的用词纠正）——已修。**
信任边界：三条 accept 路径（daemon 的 surface、runtime 的 host、以及它们的对端）。
攻击者控制：**完全**——任何能连上 runtime 端点的进程，自选 challenge，
拿到 `HMAC-SHA256(token, challenge, "step-runtime-<pid>")`，pid 可猜。
真实影响：拿到协议唯一秘密的签名能力，可在别的连接上冒充合法对等方。
另外，首帧不是 hello 的帧原本被**原样转发**，所以一个从不握手的对等方也能驱动 runtime。
**为何未修**：我试过把 `let _ = verify_hello(..)` 改成强制，e2e 立刻全红——
daemon 这一腿发来的 hello 是**请求**（无 `challengeProof`），那个调用在构造上
就不可能成功。

**拓扑（这次查清了）**：壳连 daemon 走的就是 `client.rs::connect`，它**确实**
验了 daemon 的 proof。所以这一腿是**单向**的：壳验 daemon，daemon 不验壳。
runtime 的 accept 路径则连单向都没有（`let _ =` 丢掉结果）。

**为什么不是「反转一下 challenge」这么简单**：现有 `hello_result` 的形状是
「adapter 身份字段 + 对 challenge 的 proof」，两个方向都不合适——
- 现在的方向：壳发 hello{challenge}，daemon 回「身份 + proof」。壳验了，daemon 没验。
- 反转后：daemon 要先发 hello，但 hello 里要带 adapter 身份（壳没有这些字段），
  而壳只需要回一个 proof。所以需要一个**新帧形状**，不是换谁先说话。

**具体设计（批准即可动手）**：

| 步骤 | 方向 | 帧 |
| --- | --- | --- |
| 1 | 壳 → daemon | `studio.hello`{challenge: 壳自选}（**今天的形状，保留**） |
| 2 | daemon → 壳 | `studio.hello.challenge`{challenge: daemon 新选}（**新增**） |
| 3 | 壳 → daemon | `studio.hello.proof`{challengeProof: HMAC(token, daemon-challenge, instance_id)}（**新增**） |
| 4 | daemon | `verify_hello` 验步骤 3；通过才 `serve_surface`，否则断开 |

保留步骤 1 是为了不破坏「壳验 daemon」这个已有方向，也为了让旧壳在步骤 2 就
拿到一个它能识别的错误（而不是静默断开）。代价是旧壳**会被拒绝**——它们从不
证明自己，这正是缺陷本身。

**工作量**：`handshake.rs` 加一个造 proof 应答的小函数、`client.rs` 的 connect
多读一帧多写一帧、`serve_surface` 在回答 hello 之后多一轮验证。约 100 行 + 测试。
Unix 侧可测（`daemon.rs` 那 18 条）；Windows 侧不可测，但失败模式是**响亮的**
（连不上），不是静默的。

**已落码（2026-11-18）**，四条腿全改：

| 位置 | 改动 |
| --- | --- |
| `handshake.rs` | 新增 `hello_proof`（造应答帧）与 `verify_proof`（验它），复用已有的常数时间比较 |
| `client.rs::connect` | 验完对端 hello.result 后，取出其中的 challenge，回一帧 proof |
| `bridge_server.rs`（runtime） | hello.result 里带上自己的 challenge；读一帧 proof 并**真验**（原来那行 `let _ = verify_hello` 删了——它验的是一个不可能成功的请求） |
| `adapter.rs::connect_and_handshake` | 同样应答 runtime 的 challenge |
| `studio-host.rs::serve_surface` | 自己选 challenge；首帧不是 hello **直接拒绝**（原来原样转发）；proof 不过则释放槽位并断开 |

**过程中踩到三个坑，前两个是测试告诉我的，第三个是竞态分析逼出来的**：

1. 第一次只改了 daemon 那条腿，`session.rs` 立刻红：`the peer issued no challenge to answer`。
   原因是 `client.rs::connect` 服务**两条**腿（壳→daemon 和壳→adapter），我只让一边发 challenge。
2. 补上 runtime 之后变成 **EAGAIN 超时**。原因是我用 `BufReader` 读 proof，而壳把 proof 和
   第一个真实帧**连着发**，buffering reader 把第二个一起吞了。改成不 buffering 的直读才对。
3. **而我因此自己引入了一个挂死**：第 2 条只修了 proof 那一次读，hello 那一次读**仍是
   `BufReader`**。恶意对等方把 hello 和 proof 一起发，proof 落进 hello reader 的缓冲区、
   随它一起 drop，下一步无界读永久阻塞。daemon 侧那两条读都有 `first_frame_within`
   （30 s）兜底，**runtime 侧这条没有**——不对称，且是我刚加进来的。
   修法是两次读都不用 buffering。这一条不是测试红的（现有测试走的是一来一的正常路径），
   是 Phase 2 的竞态/缓冲分析逼出来的。

还有个调试陷阱值得记：测试夹具**优先用 `target/release` 的 runtime 二进制**，
我一直在构建 debug，所以有两次改对了却看到旧行为。

**验证**：`cargo test --workspace` **375 passed / 0 failed**，含 18 条 daemon e2e 与 11 条
runtime e2e；Linux 与 Windows clippy 都 exit 0；`npm run check` 11.8 s 全绿。
破坏验证：把壳侧的 proof 发送删掉，三条 session 测试转红（`adapter closed the connection`）。

**#2 Windows peer 闸门 fail-open。** 信任边界：daemon 的 surface accept。
攻击者控制：**完全**（叠加已确认的 NULL DACL，Everyone + anonymous 可读）。
真实影响：任何本地用户可驱动他人的 session 与工作目录。
**为何未修**：`else if cfg!(unix)` 改成无条件拒绝，等于 Windows 上拒绝所有连接。

而 `OpenProcess`→`OpenProcessToken`→`GetTokenInformation` 需要 unsafe FFI，
`src-tauri`/`studio-bridge` 都继承 `unsafe_code = "forbid"`。**这是产品决策**：

一个不认证的 daemon；以及预绑定名字的 DoS。

#### `client.rs` 那侧已修（2026-11-19，提交 `667d447`），并补 fp-check 各阶段

上面这条「仍未修」在本轮关掉了：`set_read_timeout` 在 Windows 上被接受且忽略，
所以握手设的 300 s 界限在那里被静默丢弃，紧随的 hello 读可被「连上、不说话」的对端
永久阻塞——调用方既收不到错误也没有退路。修法与 daemon 侧同形：新增
`first_frame_within(reader, HELLO_BUDGET)`，建在两边共享的 `transport::wait_or_stop` 上，
平台通用；顺带让此前**零引用**的 `BridgeError::TimedOut` 变体首次被用上。

**Phase 1 数据流。** 信任边界是端点对端的进程。API 契约三条：
`set_read_timeout` 在 Unix 上界住读、在 Windows 上被接受且忽略（miow 源码已核）；
`read_frame` 阻塞在 `read_exact`；`wait_or_stop` 轮询停止标志而非取消读。
环境防护：Unix 上 SO_RCVTIMEO 300 s，Windows 上无。
交叉引用三条，其中一条**纠正了我自己的修法**：握手上游已有
`wait_for_socket(..., 20s)`，daemon 侧自己的首帧预算是 30 s；
而 `set_read_timeout` 对 reader 线程仍然有效——那正是 300 s 被从 120 s 提上去的原因
（`71312a2`「let commands overlap on one session」，命令可重叠所以读要等另一条的回合），
**与握手无关**。所以把握手读到 30 s 与上游 20 s 成比例，不是拍脑袋。

**Phase 2 可利用性。** 攻击者控制的是对端，分两种，**只有一种是攻击**：
(a) 客户端自己 spawn 的 daemon 卡住——那是可靠性问题，不是攻击，
而且「我的子进程还没回话」时挂住本就不是荒谬行为；
(b) 占端点的 squater——需要么赢过客户端自己 spawn 的那一场赛跑，
要么持有一个 client-only 会话的端点。算术 N/A。
竞态：有界读在 `spawn_reader` 接管 socket **之前**完成，所以同一时刻只有一个属主；
但 `wait_or_stop` 派出的那条线程在读提前成功后会继续睡满整个预算再去置一个
没人读的标志——**泄漏一个 sleeper，不是正确性问题**，记此不改。

**Phase 3 影响。** 这是**可用性**缺陷，按第 11 条判据（代码执行/提权/信息泄露）三者皆非，
所以**不是安全漏洞**。主控制 vs 纵深：此处根本没有安全控制可谈。
与 #5/#6 的归类修正一致——那两条也已同样重新归类。

**Phase 4 PoC。** 两条测试：静默对端在预算内被放弃；会说话的对端照旧拿到帧。
**破坏验证**：把助手改回无界阻塞读，静默那条**挂死**（120 s 被 kill），还原后两条复过。
阴阳两个方向都在。

**Phase 5（13 条中的相关项）。** 第 1 条——完整校验链是
`wait_for_socket` 20 s → `set_read_timeout` 300 s（仅 Unix）→ 新的 30 s 有界读，
三者叠加后最紧的是 30 s，这一点已在 Phase 1 说明理由；
第 3 条——可利用路径存在但收窄到「client-only 会话 + 占端点」；
第 4 条——读到的字节来自对端，squater 场景下确属攻击者可控；
第 6 条——无 TOCTOU；第 7 条——`set_read_timeout` 的平台差异是整件事的根，
这点从 miow 源码核实而非推断；第 10 条——reader 线程在有界读之后才启动，无并发属主；
第 11 条——可用性而非安全影响（见 Phase 3）；第 12 条——不适用。

**补齐此前漏掉的 5 条（2026-11-19）：第 2、5、8、9、13 条。**

  答案是不总然。而新的 `first_frame_within` 是真界限：`wait_or_stop` 依停止标志返回

  不是执行出来的——这是本项最弱的一环，写在这里而不是藏在结论里。

#### runtime 那两处为何还没修：障碍是「读者是借用的」，而放弃阻塞读必须有持有读者

`serve_connection` 有**两处**无界读，与 daemon 侧那两处一一对应：
hello（`bridge_server.rs:1156`）与 proof（`:1201`）。代码注释自己承认了这件事，
逐字：「The daemon's side of this handshake bounds both its reads
(`first_frame_within`, 30 s); this side had no bound at all.」

前两侧能修，是因为它们的读者是**持有**的：daemon 侧 `first_frame_within`
吃掉 `transport::Connection`，client 侧吃掉 `BufReader<Connection>`。
runtime 侧的读者是 `transport::handshake_reader(&mut session.stream)`——
**借用 `session.stream` 的**，而 `session` 在握手后还要用它 `send`。

**为什么不能换个懒办法绕开。** 我首先想到 `std::thread::scope`：子线程可以借用，
看起来正合适。**走不通**——`scope` 在返回前会 join 所有子线程，
所以读水死时 scope 永不返回，根本放弃不了。这正是 `wait_or_stop`
用「分离线程 + channel + 轮询停止标志」的原因，而那条路要求闭包 `'static`，
也就是要求持有读者。

于是只剩两条路，都要动共享面：

1. 给 `transport::Accepted` 加一个 `duplicate(&self) -> io::Result<Connection>`。
   `connection_duplicate` 两平台都已存在，但它吃 `&Connection`；
   `Accepted` 是平台相关 enum（Unix 只有 `Stream`，Windows 是 `Stream | Server`），
   所以这个方法要按平台各写一遍匹配。**代价：给共享 crate 加一个 API。**
2. 把 `Session.stream` 的字段类型从 `Accepted` 改成 `Connection`，
   于是一开始就能复制一份给有界读用。**代价：动到 `Session` 的每一个使用点
   （`send`、`handshake_reader` 两处），且 `handshake_reader` 的签名吃 `&mut Accepted`，
   连带要改它。**

两条都不是十行以内，且都碰到共享 crate 的 API 形状——按 §19 对 #2 的同一条纪律，
**这属于要先定形状再落码的事，不是代码大小问题**。记下障碍与两条路的代价，
下一个拿到这里的人不用重新发现「scope 不行」和「读者是借用的」这两点。

runtime 的 hello 与 proof 两处读**也已修**（`85bb272`）。三侧全部修毕。

#### runtime 那两处读的 fp-check 各阶段与裁决（2026-11-19 补）

**一个先于各阶段的事实，它改严重度**：全仓 grep `set_read_timeout`，

不像 `client.rs` 至少 Unix 上有 300s 兜着。同族三处里这一处最松。

**Phase 1 数据流。** 信任边界是连上 runtime 端点的对端进程。
API 契约三条：`transport::handshake_reader(&mut session.stream)` **借出**读者
（Unix 返回 `impl Read + '_`，Windows 返回 `&mut Accepted`）；
`read_frame` 阻塞在 `read_exact`；`serve_one` spawn 后**立即 join** worker。
环境防护：**无**——该 crate 不设任何读超时。
交叉引用：`serve_connection` 的注释自己写着「this side had no bound at all」，
且 accept 循环 join worker，所以一个卡住的连接会挡住后续 accept
（与 daemon 的「唯一槽位」不同形，但同样是一次一个）。

**Phase 2 可利用性。** 攻击者控制的是对端。两种情形：
(a) daemon 卡住——同用户进程，可靠性问题；
(b) 占 runtime 端点的 squater——攻击。算术 N/A。
竞态：**这里与 daemon 不同**——daemon 是「先到先得串行化，无 TOCTOU」，
runtime 是 accept 循环 join worker，所以卡住的连接**阻塞后续 accept**，
这是资源耗尽而非竞态；无 check-then-use 时间窗。
对抗分析：squater 需先占住 runtime 的端点，其暴露面低于 daemon 的
（daemon 端点是壳主动连的那个）。

**Phase 3 影响。** 可用性缺陷。按第 11 条判据三者皆非，**不是安全漏洞**。
主控制 vs 纵深：此处无安全控制可谈。与 #5/#6、client.rs 归类一致。

**Phase 4 PoC。** **修复后有 PoC，但只有组合层面的，没有直接打到这两处调用点的。**

### Q1：challenge 必须由验证方选——NIST 原句

SP 800-63B-4（当前修订版，2025-08-26）词条 **challenge-response protocol**：

> An authentication protocol in which the **verifier sends the claimant a challenge**
> (e.g., a random value or nonce) that the claimant combines with a secret … to
> generate a response that is sent to the verifier.

同文件 §5：

> Single-factor cryptographic verifiers **generate a challenge nonce, send it** to the
> corresponding authenticator, and use the authenticator output to verify possession
> of the authenticator.

> The challenge nonce **SHALL** be at least 64 bits in length and **SHALL** either be
> unique over the authenticator's lifetime or statistically unique.

**而 RFC 4949 的词条区分，正是 #1 的准确表述。** claim 方自选 challenge 最多只到
**data origin authentication**（「the corroboration that the source of data received
is as claimed」—— tutorial 明说它与收发双方的关系无关、数据可能来自过去任意时刻），
**到不了 peer entity authentication**，因为它没有建立 **liveness**
（「provides assurance to the recipient of data that the data is being freshly
transmitted by its originator, i.e., that the data is not being replayed」）。

「server 先说话」没有单独的名字：它就是 challenge-response，只是 challenge 由
验证方生成。标准范式是 **CHAP（RFC 1994 §4.1）**：

> **The authenticator MUST transmit a CHAP packet with the Code field set to 1
> (Challenge).** … **Whenever a Challenge packet is received, the peer MUST transmit
> a CHAP packet with the Code field set to 2 (Response).**

### 我的一处用词被纠正

我在 §17 把 #1 叫「**signing oracle**（签名预言机）」。**这不是术语**——专家 grep 了
RFC 4949 全文：没有 `challenge` 条、没有 `oracle` 条、也没有 `masquerade attack` 条。
这个失败的标准化词汇是**缺失的那个属性**（liveness / peer entity authentication），
不是 bug 的名字。我描述的现象是真的，但我给它起的名字是我自己的，不该看着像术语。
下文改称「**claim 方自选 challenge 的验证器**」。

### Q2/Q3：Windows 侧没有「安全且有人维护」的路——这一条从假设变成查证

我此前写 #2「需要 unsafe」。专家按候选清单逐個查了，结论是**没有安全且维护中的
通用 crate 做这件事**：

| 候选 | 存在 | 维护 | 需要 unsafe |
| --- | --- | --- | --- |
| `windows` 0.62.2 / `windows-sys` 0.61.2 | 是 | 是（2026-11-18 有推送） | **是**（`GetNamedPipeClientProcessId` 与 `GetTokenInformation` 都是 `pub unsafe fn`） |
| `named_pipe` 0.4.1 | 是 | **否**（2019-04-07 归档） | 无此 API |
| `tokio::net::windows::named_pipe` 1.54.1 | 是 | 是 | 无此 API |
| `miow` 0.6.1 / `interprocess` 2.4.8 | 是 | 是 | 无此 API |
| `std` | — | — | 无任何相关 API |
| `felis-transport` 0.3.0 | 是 | **一个月新**，140 下载 | 否——但它是单个终端模拟器项目的 IPC 层 |

DACL 那一侧：`windows-permissions` 0.2.4 **确有**对
`ConvertStringSecurityDescriptorToSecurityDescriptor` 与 `SetNamedSecurityInfo` 的

### Q4（2026-11-19 补）：选项 1 的路不止一条，而且方案记的那条不是最好的一条

Q2/Q3 查的是「有没有 crate 替你包装」，结论是没有。但没问另一个问题：
**Win32 自己为「服务端认出客户端是谁」提供的规范机制是什么**。查证结果，
方案里记的 `GetNamedPipeClientProcessId` → `OpenProcess` → `OpenProcessToken` →
`GetTokenInformation` 这条路，**不是** Microsoft 文档指向的那条。

Microsoft 的 [`ImpersonateNamedPipeClient`](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient)
参考页， Remarks 逐字：

> the named-pipe file system changes the thread of the calling process to start
> impersonating the **security context of the last message read from the pipe**.

配套的[概念页](https://learn.microsoft.com/en-us/windows/win32/ipc/impersonating-a-named-pipe-client)：

> A named pipe server thread can call the **ImpersonateNamedPipeClient** function
> to assume the access token of the user connected to the client end of the pipe.

于是取对端用户 SID 的规范序列是：读一帧 → `ImpersonateNamedPipeClient(hPipe)` →
`OpenThreadToken(GetCurrentThread(), TOKEN_QUERY, …)` → `GetTokenInformation(TokenUser)`
→ `TOKEN_USER.User.Sid` → `RevertToSelf()`。

**这条路与方案已记的那条有三处实质差别：**

| | 方案已记（PID 锚定） | 规范机制（模拟） |
| --- | --- | --- |
| 是否依赖 PID | 是——**Project Zero 的结论正打在这里**：「client PID 不应被用于安全决策」 | 否，完全不经过 PID |
| 是否要 `OpenProcess` | 是（多一个句柄生命周期与竞态面） | 否 |
| SID 的来源 | 进程 token（要猜哪个进程） | 线程 token，即「最后读到的那一帧的发送者」，无猜测 |

**同一页还给了两条直接可用的东西。** 其一，模拟被允许的条件，逐字列了四项，
第四项是：

> The authenticated identity is same as the caller.

即**对端是同一用户时不需要任何特权**。其二是一条 fail-closed 要求：

> To avoid security risks, the calling process should always check the return value.
> If the return value indicates that the function call failed, no client requests
> should be executed.

**`SeImpersonatePrivilege` 的默认持有者**（Microsoft 安全策略页
[Impersonate a client after authentication](https://learn.microsoft.com/en-us/windows/security/threat-protection/security-policy-settings/impersonate-a-client-after-authentication)）：
Administrators、LOCAL SERVICE、NETWORK SERVICE、SERVICE。**标准用户不在其中。**

**这条推理是错的，2026-11-19 当天被 fp-check 的 Phase 5（魔鬼代言人）推翻。**
原文四项条件的**第一项**逐字是：

> The requested impersonation level of the token is less than **SecurityImpersonation**,
> such as **SecurityIdentification** or **SecurityAnonymous**.

而我先前核过的概念页明写：

> when the client calls the **CreateFile** function to open a handle to the client end
> of the pipe, the client can use the SECURITY_SQOS_PRESENT flag to **control the
> server's impersonation level**.

即**对端自己选模拟级别**。而 `\.\pipe\` 的 DACL 已核实是 Everyone + anonymous 可读，
所以一个**不同用户**的恶意对端可以：连上 → 用 `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`
打开 → `ImpersonateNamedPipeClient` **成功**（命中第一项条件）。
于是「成功 ⇒ 同一用户」不成立，**据此写的「不必再比 SID」是错的，已推翻**。

魔鬼代言人这一轮值得记的是：推翻它的两条证据，我**在写 Q4 的同一轮里都已经拿到过**
（四项条件的清单我逐字引了，概念页的 SQOS 那句我也逐字引了），只是没把两者放到一起推。
单条引用都正确，合起来的推论是错的——这正是 Phase 5 存在的理由，
也是为什么「我引用了原文」不等于「我的结论站得住」。

**修正后的正确形状**：模拟 → `GetTokenInformation(TokenUser)` 读 SID →
**与 daemon 自己的用户 SID 比对**，不等则拒。SID 比对**不是可选的加固，是必需的**。
好消息是 `SecurityIdentification` 级别恰恰就是为「只查身份、不代为行事」设计的，
所以 `GetTokenInformation(TokenUser)` 在该级别下依然有效——读 SID 这条路不受影响，
受影响的只是那个想省掉它的捷径。

第三项条件（显式凭据 token，`LogonUser`/`LsaLogonUser`）在索引副本里被截断
（止于 "A process (or anothe…"），未取到全文；它与本纠正无关，记此备查。

**这不溶解决策，只改形状。** 四条 FFI 仍是 `pub unsafe fn`，`unsafe_code = "forbid"`
仍要被破一次，所以 Q2/Q3 的三个选项一个都没少。变的是要开的那条例外**更小、
更好辩护**：不碰 PID（躲开 Project Zero 的结论）、不 `OpenProcess`、
用的是 Microsoft 为这个目的文档化的机制，且 Microsoft 自己规定了失败时必须拒绝。

**三条必须一起记的限定：**

1. **两条会让「读到的身份」变弱的路径，都不是提权那条最常见**：
   - 对端用 `SECURITY_SQOS_PRESENT` 自选更低的模拟级别（`SecurityIdentification`），
     于是 `ImpersonateNamedPipeClient` 对**不同用户**也会成功——这条**已经被
     Phase 5 证实可走**，也正是「必须比 SID」的原因；
   - 用户以 Administrator 运行壳，daemon 持有 `SeImpersonatePrivilege`，
     模拟对任何用户都成功——这条**理论上成立，但因为反正要比 SID，已无害化**。
   两条合起来的结论：**只读 SID 并比对**，不要试图从「模拟成没成功」推断身份。
2. **「先读后模拟」是精确前提**：模拟用的是「最后读到的那一帧」的上下文，
   所以必须在本协议已有的 hello 帧之后调用——这一点与现存的 mutual handshake
   恰好对齐，不需要新增往返。
3. **命名管道模拟是已知的本地提权原语**（Potato 一族），但那是**服务端持有客户端
   所缺的特权**时才有意义。本 daemon 是每用户进程，不持有额外特权，
   所以这条不适用于此处——记下来是因为下一个人查到这条时会问。

**未验证**：以上全部来自 Microsoft 文档与安全策略页，本机无 Windows，
没有一条在 Windows 上实跑过。提案形状如此，实施前需一台 Windows 机器。

#### Q4 提案自身的 fp-check 各阶段（2026-11-19 补）

上面 Phase 5 只翻了结论，没审提案。这个提案要驱动项目负责人的决策，
所以其余阶段一并补上，弱的地方直接写弱。

**Phase 1 数据流。** 三个信任边界，不是一个：
(a) 管道 DACL——谁能连上（已核实 NULL，Everyone + anonymous 可读）；
(b) `ImpersonateNamedPipeClient`——线程取谁的身份（由「最后读到的那一帧」决定）；
(c) SID 比对——真正的闸门。API 契约两处：`ImpersonateNamedPipeClient` 只收管道句柄，
身份不自参数来；`GetTokenInformation(TokenUser)` 需要对线程 token 的 `TOKEN_QUERY`。
交叉引用一点是**有利的**：现存 mutual handshake 本来就要求对端先发一帧才继续，
所以「先读后模拟」这个前提已经被现有协议满足，不需要新增往返。

**Phase 2 可利用性。** 攻击者可控：**模拟级别可控**（SQOS，已证）、到达哪些帧（可控）、
hello 内容（可控）。攻击者**不可控**：SID 的值（OS 分配）。
算术：N/A。竞态：不是竞态而是**顺序约束**——模拟取的是「最后读到的那一帧」，
所以实现必须在读完 hello 之后、读下一帧之前调用；daemon 是单连接串行模型
（一个时刻一个 surface），同线程不会交错，但实现顺序写错会读到错误帧的上下文。

**Phase 3 影响。** 若省掉 SID 比对，任何本地用户可驱动他人的 session 与工作目录——
即 #2 的原始影响，一分不少。且这是**主控制**而非纵深：#1 管认证，这个管授权，
是 #2 授权侧唯一候选。

**Phase 4 PoC。** **明确跳过，理由是本机无 Windows**：连接、SQOS 标志、
`ImpersonateNamedPipeClient`、`GetTokenInformation` 全部需要 Windows 真机。
可写的只有伪代码（攻击序列：连上 → SQOS 标识级打开 → 发 hello → 令 daemon 模拟 →
若 daemon 只凭「模拟成功」放行，则跨用户得逞）。Unix 侧同属性已有可执行 PoC
（`peer_may_serve` 的两条断言），Windows 侧那条 `an_unidentifiable_peer_is_accepted_on_windows_which_is_th13`
只证明缺口在场，不证明修复有效。

它确认了路线与 Phase 5 的纠正，另外给出四条此前方案里没有的东西：

**1. 默认 DACL 的记录不完整——这是对已有记录的纠正。** 方案多处写「NULL DACL，
Everyone + anonymous 可读」。`CreateNamedPipe` 的原文更细，逐字：

> If `lpSecurityAttributes` is `NULL`, the named pipe gets a default security
> descriptor … The ACLs in the default security descriptor for a named pipe grant
> **full control to the LocalSystem account, administrators, and the creator owner**.
> They also grant **read** access to members of the Everyone group and the anonymous account.

即创建者属主拿到的是**完全控制**，Everyone 只有**读**。专家还标出一个我们没验的推断：
文档说的是 read，一个请求 `GENERIC_READ|GENERIC_WRITE` 的客户端能否连上**未经实测**。
这条要单独验，因为它决定暴露面是「只读」还是「可写」。

**2. 「模拟成功」不是认证——把 Phase 5 的纠正说得更锋利。** `ImpersonateNamedPipeClient`
在 `SecurityAnonymous` 下也会成功。所以 `if !impersonate { reject }` **不是有效检查**：
传 `SECURITY_SQOS_PRESENT | SECURITY_ANONYMOUS` 的对端直接穿过，而你会读到
`S-1-5-7`（`NT AUTHORITY\ANONYMOUS LOGON`）。**必须比 SID，并对匿名 SID fail closed。**

**3. 同一 SID ≠ 同一进程或同一会话**——这是对我方威胁模型边界的一条澄清。
同一账户的两个并发 RDP 会话、计划任务、以该用户运行的服务，user SID 全都相同。
所以这道闸门回答的是「哪个**用户**」，不是「哪个**进程**」。我方 TH13 的攻击者
定为「另一个本地用户账户 / 匿名账户」，因此不受影响；但**必须写清楚**，
否则下一个人会以为它防住了同用户的其他进程——那个由 #1 的 token 管。

**4. 一个方案没记的读取面。** 专家指出：DACL 给 Everyone 读权限，
而 token 认证只门控 client→daemon 方向，所以任何本地用户都能连上并**读 daemon 写给它的东西**。
这条**未经我方核实，不作为结论**——daemon 在握手成功前是否向连接写任何内容，
决定这个面是真空还是有料。已记为待查。

另外专家取到了我此前没取全的**第三项条件**逐字：

> A process (or another process in the caller's logon session) created the token
> using explicit credentials through `LogonUser` or `LsaLogonUser` function.

**实现层的五条约束**（专家给出，均与其引用的文档对应）：
`EqualSid` 比对而非字符串比对；daemon 自己的 SID 从**进程 token** 取而非硬编码账户名；
`RevertToSelf()` 必须在每条路径上执行（含错误与提前返回）；
整个 读→模拟→查→还原 序列必须在**同一个线程**上完成（模拟附着于调用线程）；
只授权 user SID，不要授权组成员身份——`SECURITY_EFFECTIVE_ONLY` 能让客户端对自己的组与特权说谎。

#### Q4 提案的 13 条假阳性清单（2026-11-19 补，fp-check skill 已加载后逐条做）

此前我以「13 问定义在我没有加载的 skill 里，猜着答等于编」为由跳过。
这个理由不成立——那个 skill 我可以加载。加载后逐条应用，**又翻出两个我自己没验的东西**：

**第 1 条（追溯完整校验链）与第 12 条（纵深 vs 主控制）合起来，指向同一个此前没答的问题。**
往回追，SID 闸门**之前**已经有一道校验：#1 的 mutual handshake 要求对端证明持有 token 文件，
而该文件是 `0600` 且在 `0700` 目录里。所以能走到 SID 闸门的对端，**已经**被要求
「能读那个 token」。于是问题变成：一个**不同用户**的进程有没有可能通过 #1？
- 若 token 权限可靠（0600/0700 成立），答案是不可能——那么 SID 闸门就是**纵深**，
  按第 12 条，「纵深机制失效不必然是漏洞，若主控制存在」；
- 而本会话早前正好核实过 token 权限**曾经不成立**（umask 664，组可写，已修）。

**所以 #2 的定级取决于一个会变的事实**：token 权限修好之后，#2 从「主控制缺失」
向「纵深失效」移动了。方案目前把它记成 TRUE POSITIVE + 真实影响，
这个定级是在 token 修好**之前**做的，**没有随之重新定级**。这不是要把 #2 降级，
而是指出定级的前提变过，需要项目负责人明确一次：token 0600 是否被视为可靠前提。

**第 7 条（API 契约）翻出我一处无出处断言。** 我在 Q4 里写
「`SecurityIdentification` 级别恰恰就是为『只查身份』设计的，所以
`GetTokenInformation(TokenUser)` 在该级别下依然有效」——**这句话我当时没有出处**。
我是从级别名字推断的，而级别名字正是第 9 条警告的「模式识别 ≠ 分析」。
这是 Q4 里第三个需要验证而没验证的点，且它是**载荷的**：
若标识级别下读不到 `TokenUser`，整条路线要重新设计。

**现已补检索，断言成立，出处逐字如下**（Microsoft
[Impersonation Levels](https://learn.microsoft.com/en-us/windows/win32/secauthz/impersonation-levels)
的四级表）：

| 级别 | Microsoft 原文 |
| --- | --- |
| `SecurityAnonymous` | The server cannot impersonate **or identify** the client. |
| `SecurityIdentification` | The server **can get the identity and privileges** of the client, but cannot impersonate the client. |
| `SecurityImpersonation` | The server can impersonate the client's security context on the local system. |
| `SecurityDelegation` | The server can impersonate the client's security context on remote systems. |

所以标识级别下**能**拿到客户端身份，`GetTokenInformation(TokenUser)` 这条路成立。

**但同页还多给了一条此前没记的要求**：`SecurityAnonymous` 是「不能模拟**也不能识别**」。
而对端**能自选级别**（同页：「The client of a named pipe … **can control the impersonation level**」，
并点名命名管道客户端用 `CreateFile` 指定服务端的模拟级别）。于是一个恶意对端可以请求
`SecurityAnonymous`，让识别**根本不可能发生**——SID 读不出来。

**这对实现是一条硬要求，不是可选加固**：SID 读不到时必须**拒绝连接**，
而不是放行。它与 Microsoft 在 `ImpersonateNamedPipeClient` 页自己写的那条
fail-closed 要求同向（「若函数失败，不应执行任何客户端请求」）——
两处合起来，这个闸门的形状是「拿不到可信身份就拒」，而不是「拿不到就放过」。

另记一条同页事实，它让默认情形更安全：**`SecurityImpersonation` 是命名管道、
RPC、DDE 服务端的默认级别**。即行为端正的对端不需要做任何事就在可识别级别上；
只有**主动**请求更低级别的对端才需要被 SID 比对挡住。

**其余各条的结论**（逐条有依据，不展开）：
第 2 条——SID 比对不是防御性断言，是唯一能识别「持 token 的非属主」的机制；
第 3 条——可利用路径存在但收窄到「token 权限失效」一种；
第 4 条——SID 由 OS 分配不可控，模拟级别由对端可控（已证）；
第 5 条 N/A；第 6 条——无 TOCTOU，但是顺序约束（最后读到的那一帧）；
第 8 条 N/A；第 9 条——路线变更出自读文档而非模式匹配；
第 10 条——单连接串行，无并发，但实现顺序写错会读错帧的上下文；
第 11 条——真实影响（跨用户驱动），但需先过 #1；
第 13 条——本轮即是。

```
3. daemon：peer_may_serve(None) → 放行                    # ← 缺口：这里本应拒
4. B 驱动 A 的 session

# ── 阴性 PoC：修复在场，攻击失败 ────────────────────────────────
1-2. 同上
3. daemon：ImpersonateNamedPipeClient → GetTokenInformation(TokenUser) → SID_B
           EqualSid(SID_B, 自己的 SID) → false → 拒        # ← 修复起效的位置
4. B 被拒，槽位释放

# ── 附带攻击：只凭「模拟成功」放行会被这条打穿（Phase 5 的那个错误） ──
1. B 连上，CreateFile 时带 SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION
2. daemon：ImpersonateNamedPipeClient → 成功               # 命中条件一：请求级别 < SecurityImpersonation
3. 若代码在此放行 → B 跨用户得逞                          # 所以必须比 SID，不能看成功与否
```

**可执行 PoC 跳过**：三步全部需要 Windows 真机（连接、SQOS 标志、两个 Win32 调用），
本机无 Windows。这与 §21 里 #2 的 PoC 状态一致：Unix 侧有可执行 PoC，
Windows 侧只有「缺口在场」的断言，没有「修复有效」的断言。

### 伪代码 PoC（2026-11-19 补）：#2 与 #4

fp-check 的 Phase 4 把「伪代码 PoC」和「可执行 PoC」分成两项，前者的跳过条款只覆盖
后者。所以对没有可执行 PoC 的 #2 和 #4，伪代码那一项不是不适用，是欠着。补上。

#### #2 Windows peer 闸门 fail-open

```
# 前置条件（都已核实）：NULL DACL → Everyone + anonymous 可读（Microsoft 原文）；
#                         `peer_uid` 在 Windows 上恒返回 None（peer-uid 的 Windows 测试钉住）
# 攻击者：另一本地用户账户，不需要任何 token

1. handle = CreateFileW("\\.\pipe\\step-studio-<hash(victim-USERNAME)>",
                        GENERIC_READ | GENERIC_WRITE, ...)
   # peer 闸门：serve_surface 调 peer_uid(handle) -> None
   #             peer_may_serve(None) == !cfg!(unix) == true  → 放行
   #             （Unix 上这条是 false，连接在此被拒）

2. 之后发生什么，取决于 #1 是否已修：
   - #1 修复前：直接发 studio.request，驱动受害者的 runtime
   - #1 修复后：daemon 先发 challenge，攻击者无 token → proof 失败 → 断开

3. 残余影响（#1 之后）：成功占用一次 surface 连接，并在 proof 步才被拒
```

**这个 PoC 证明的是**：peer 闸门本身不拒绝任何东西。它**不**证明攻击者能驱动会话——
那条路已被 #1 堵住。两者都要说，只讲前者是夸大，只讲后者是漏报。

#### #4 管道名来自 `USERNAME.len()` → 预绑定 DoS

```
# 前置条件：default_endpoint() == "step-studio-" + USERNAME.len()
#           \.\pipe\ 是机器级单一命名空间（不是 per-user）
# 攻击者：能注册一个自选长度用户名的本地账户

1. 注册用户名，使 len(用户名) == len(受害者用户名)      # 长度可枚举，不需要知道名字
2. 以该用户登录，先启动自己的 daemon
   → 它 bind 的正是受害者 daemon 要 bind 的同一个管道名
3. 受害者的 daemon 启动：CreateNamedPipeW 失败（名字已被占用）
   → 受害者的壳连不上，且日志只显示一次 bind 失败

# 不需要 token、不需要对等身份、不需要任何认证
```

**这个 PoC 证明的是**：管道名空间冲突可被**主动构造**，而不只是"同长度用户偶然相撞"。
`stable_discriminator`（FNV-1a）修掉了它。

**但"计算上不可行"这个说法是错的，别这么写。** FNV-1a 输出 `u32`，只有约 40 亿个值；
攻击者要撞的是**受害者那一个特定管道名**，即找一个原像，这在攻击者本机上是**离线可算的**
（不需要注册任何账户去试，几十亿次哈希是秒级），算完只注册一个账户即可。
所以哈希并没有把碰撞变成计算上困难——它只是把"枚举长度"（个位数次尝试）
变成了"找一个原像"（一次离线计算）。

**真正的屏障在别处**：在 Windows 上创建本地用户账户需要管理员权限，
而一个已经是管理员的人有比撞管道名直接得多的路。换句话说，
#4 的残余影响不是被哈希挡住的，是被"攻击者需要先已经是管理员"挡住的——
这与 S2 判定 #2 时用的推理同形（见 §17 S2：管理员本就可为所欲为，
所以那部分不构成额外攻击面）。**结论不变但理由要换**：哈希值得做（它让偶然碰撞
和长度枚举都消失），但别把它当成访问控制，真正的修法仍是 S2 的 SID 闸门。

### 裁决汇总

**6 个 TRUE POSITIVE，1 个 FALSE POSITIVE**（#7，见下）。6 个已修并带会红的 PoC，
#2 已修一半（认证侧经 #1 补偿）但授权侧未修，卡在 unsafe 例外这个决策上。

#### #7 是 FALSE POSITIVE，而它是被 fp-check 的假阳性清单翻出来的

审评的表述是「三个 writer 只有一个 chmod，所以 *它们创建* 的 token 文件是 umask 默认」。
机制没错，**但创建那条路径生产里不走**：

- 两个生产 launch 点都传 `token: Some(..)`（壳读 `state::token_path()`，TUI 同样），
  所以 `client.rs:140` 的 mint 分支没有生产调用方——只有测试走它。
- `adapter.rs:116` 写的是 `state::token_path()`，而 daemon 在 `main` 里**先 mint 再 serve**，
  文件早已是 `0600` 且在 `0700` 目录里；裸 `fs::write` 截断而不改模式，所以暴露不成立。

实测过那个 664（`/tmp` 下复现 `.step-studio` 目录与 token 文件），但那是**新建文件**的场景，
而生产里没有一个新建者。

**修复保留**，理由说准：它让 `token.rs` 文档声称的 0600 在每个路径上都成立，
属于清单第 12 条（defense-in-depth）而非第 11 条（real impact）。
但把它记成 TRUE POSITIVE 是错的，已改。

顺带查出的 `.step-studio` 目录问题**本轮已修**：它由 `create_dir_all` 建、
原本没有任何加固，实测 `0o775`（umask `002`）——组可写，而同组其他人可以替换
里面那个 token 文件。TH2 为 daemon 的端点目录做了 `0700` + 属主校验，
这一处漏了。已补同样的硬化，实测 `0o775 → 0o700`。

**没有 FALSE POSITIVE 值得单独说**：审评报了 7 项，我核实了 7 项，没有一项是误报。
但有过三次**我自己的假阴性/假阳性**（§15 的 3→2、§16 的 lib-only 会产出 33% 假阳性、
T4 驱动 sed 弄坏后 13 行全红），那些是工具与过程的错误，不是审评的错误——记在各自节里。

### 自比较模式的库内扫描（2026-11-19）

`platform.rs` 那条空泛测试的形状是「assert 两边是同一个函数」，于是库内扫了一遍：
`assert_eq!` 两侧出现同名函数调用的共 **7 处**。逐个看过，**没有第二处有害形态**——
其余六处都另有绝对断言扛重量，自比较只额外钉"确定性"：

| 位置 | 绝对断言 | 自比较的角色 |
| --- | --- | --- |
| `swap.rs:352` | `aside_path(target) == /opt/….previous` | 额外钉"两次 swap 复用同一个 aside 名" |
| `prediction.rs:705-707` | 名字以 `p-` 开头、长度 = 前缀 + 16 hex + 后缀 | 额外钉"对同一 id 稳定" |
| `lifecycle.rs:356` | 三组 `assert_ne!`（同长度不同名、空串 vs 单字符） | 额外钉"同输入同输出" |
| 其余三处 | `len()` 对比 | 长度算式，非同构比较 |

有害形态（自比较是唯一守卫、且注释声称它能发现分歧）全库只出现一次，就是 `platform.rs` 那条。
记下来免得下轮重扫。
