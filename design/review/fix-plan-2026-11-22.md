## 二、波次划分

排序原则：**先让门禁可信，再修功能，再补流程基线**。没有绿门禁，后面每一项的「已验证」都不可信。

```
W0 止血 ──┬─ #3 干净检出        （门禁可信的前置）
          └─ #1 环境变量契约     （我引入的回归，有用户可见后果）
W1 可运维 ── #2 日志             （依赖 W0 的门禁才能验证）
W2 功能 ──── #5 私有目录注入     （依赖 #1 的契约修复先落地）
W3 流程 ────┬─ #6 收尾           （小，可随时插空）
          ├─ #7 供应链基线
          ├─ #8 发布口径         （依赖 #7 的锁定与 #3 的门禁）
          └─ #9 macOS 覆盖       （依赖 #8 的安装包 job 存在）
W4 质量 ────┬─ #10 前端门禁      （独立，可全程并行）
          └─ #11 兼容策略        （依赖 #10 的覆盖率门禁兜底重构）
```

## 三、逐项设计

### W0-1 · #3 让 `check` / `build` 从干净检出通过

**根因**（三处，互相独立）：

1. `scripts/check.mjs:279` 把 `contracts` 步骤排在编译之前，而它读
   `packages/studio-protocol/dist/src/index.js`。干净树上没有 `dist/`，
   `ERR_MODULE_NOT_FOUND`。注释自己写着「Runs after the builds」——注释与顺序矛盾。
2. `packages/runtime-installer/src/update-index.ts:13` import `@step-studio/client-contract`，
   但 `package.json` 只声明了 `studio-protocol`。靠 npm 提升侥幸解析成功，干净树 `TS2307`。
3. `package.json` 的 `build:packages` 把 `transport-desktop` 排在 `client` 之前，而前者 import 后者。

**修法**：

- 1：`contracts` 移入编译之后的组。`check.mjs` 已有 `levels(closure(...))` 的拓扑实现，
  `build:packages` 改为调用同一个排序，消掉「脚本顺序靠人肉维护」这一类根因。
- 2：这是**分层决策，不是补一行声明**。两个选项：
  - **A（推荐）**：`update-index.ts` 不再 import `client-contract`，改用 `studio-protocol`
    已有的版本常量，或把需要的常量下沉到 `studio-protocol`。保持 `runtime-installer` 只依赖
    `studio-protocol` 的现有约束。
  - B：声明依赖并修改 `architecture.test.mjs:31` 的白名单。会放宽一条真实的分层约束，
  需要单独评审。
- 3：`build:packages` 改为拓扑排序输出，不再手写顺序。

**验证**：

```bash
git clone <repo> && cd <repo> && npm ci
find packages apps -maxdepth 2 -name dist -type d -exec rm -rf {} +
npm run check -- --production     # 必须一次通过
npm run build:packages            # 必须从零通过
```

**回滚**：三项都是脚本/声明改动，`git revert` 单次提交即可；无数据迁移。

### W0-2 · #1 恢复 host↔Runtime 的两条环境变量契约

**根因**：`ea787b9` 把宿主侧 `OMP_*` 统一改成 `STEP_STUDIO_*`，但 overlay（编译进 `step` 的代码）
按设计不在那次改动范围内。两条**跨进程**契约因此两侧名字对不上：

| 契约 | 宿主侧 | Runtime 侧 |
|---|---|---|
| 父进程看门狗 | `runtime-resolver.ts:713` 设 `STEP_STUDIO_PARENT_PID` | `parent-watchdog.ts:13` 读 `OMP_STUDIO_PARENT_PID` |
| 统计面板不拉起浏览器 | `omp-usage-adapter.ts:162` 设 `STEP_STUDIO_STATS_NO_OPEN` | `stats-cli.ts:76` 读 `OMP_STATS_NO_OPEN` |

用户可见后果：① 统计页额外拉起一次系统浏览器（CHANGELOG 0.1.17 刚修好的回归）；
② macOS 上宿主强退后 Runtime 不自我退出，`step_rpc.rs:266` 的兜底只 `child.kill()` 直接子进程、
不是进程组，工具与子代理会残留。

**修法**：**宿主侧回退到 `OMP_*` 拼写，而不是改 overlay 侧。**

理由：这两个名字本身就是兼容契约。`stats-cli.ts` 的注释写明「这是环境变量而不是 flag，是为了让
按旧 Runtime 写的宿主继续可用」——它的存在意义就是让不同版本的宿主都能驱动 Runtime。
把宿主侧改回 `OMP_STUDIO_PARENT_PID` / `OMP_STATS_NO_OPEN`，契约恢复，且不影响
`STEP_STUDIO_*` 家族其余 23 个本仓库内部变量。

**同时加生成式契约门禁**（issue 的「期望」部分，也是唯一能防再犯的东西）：

- 单一事实源：在 `packages/studio-protocol` 或等价位置声明一张「跨进程环境变量契约表」，
  每条含名字、设置方、读取方、用途。
- 生成式检查：一个脚本从契约表生成两侧的字面量，或在编译期/门禁期比对
  「宿主侧设置的集合」与「overlay 侧读取的集合」，交集为空即失败。
- 当前两侧集合（宿主 25 / overlay 14，交集 1）就是这条门禁的第一个断言。

**验证**：门禁断言 + 两个既有测试（`omp-usage-adapter.test.ts`、
`parent-watchdog` 相关）；macOS 进程组行为需要真机，列入未验证清单而不是假装通过。

**回滚**：宿主侧两个变量名改回，单次提交；契约表是新增文件，删掉即回退。

### W1 · #2 daemon 日志追加 + 轮转

**根因**：`bridge.rs:606` 用 `File::create`（存在则截断）；路径解析有两份拷贝
（`bridge.rs` 的 `cwd.join(".step-studio")` 与 `chrome.rs` 的 `state_dir_from(cwd)`），
回退分支（CWD 不可写时写 `%TEMP%`）只在写入侧存在，导出侧不认。

**修法**：

- 打开方式改 `OpenOptions::new().create(true).append(true)`。
- 轮转：8 MiB × 3 份，按启动时检查 + 写入时检查两级；保留至少 7 天。
- **单一来源函数**：抽出 `daemon_log_path()`，`bridge.rs` 写入与 `chrome.rs` 导出共用同一个
  （含回退路径）。这是根因修复——两份路径拷贝是「回退情况下导出按钮失灵」的直接原因。
- 渲染层 `ErrorBoundary` → `reportWorkbenchFailure` → `chrome.rs:729` 的 `eprintln!`
  改为写入同一份日志，带版本、epoch、错误码。
- **脱敏**：日志中不得出现 bridge token、API key、完整 prompt（ASVS 7.1.1/7.1.2、CWE-532）。
  这一条要有一个测试钉住，否则迟早有人把 token 打进去。

**验证**：两次启动间行数累积；回退路径下导出按钮能找到日志；轮转触发；
一条「token 不出现在日志里」的断言。

**回滚**：纯 Rust 侧改动，无数据迁移；轮转是新增行为，关掉开关即回到追加模式。

### W2 · #5 Runtime 私有目录注入

**根因**：`media-service.ts` / `live-audio-service.ts` / `prediction-service.ts` /
`browser-observation-service.ts` / `auth-broker-service.ts` 五个服务靠
`OMP_STUDIO_MEDIA_ROOT`、`OMP_STUDIO_SOCKET_DIR`、`OMP_STUDIO_AUTH_BROKER_FILE` 拿私有目录，
而全仓没有任何进程设置它们；构造点 `workbench-service.ts:195` 是 `new StudioMediaService(session)`，
不注入依赖，所以只能走 env。

**修法**：

- daemon 启动时为这三个变量准备目录：用户 state 目录下，权限 `0700`，属主校验
  （复用 `state.rs` 的 `prepare_dir_at` 既有实现，不新写一套）。
- **依赖 W0-2 的契约表**：这三个变量正是跨进程契约，应该进那张表，由门禁保证有写入方。
- 目录缺失/创建失败时**报出原因到诊断页**，而不是静默 `available: false`。

**验证**：全新安装（不设任何环境变量）下媒体页 `available: true`；
诊断页能看到目录路径与失败原因；一条「服务可用性不为 false 时不带原因」的断言。

**回滚**：daemon 侧新增环境变量设置，撤掉即回到现状；overlay 侧只读不改。

### W3-2 · #7 供应链基线

**修法**：

- 所有 `uses:` 固定到完整 commit SHA；Dependabot 负责升级（否则钉 SHA 后没人能动）。
- `.github/dependabot.yml`：`github-actions` / `npm` / `cargo` 三个生态，分周批次。
- `.github/CODEOWNERS`：host / runtime / renderer / CI 四个面。单人项目就写成「角色帽」，
  把责任落到面而不是人。
- JS 侧加 `npm audit --omit=dev` 与许可证白名单（与 `deny.toml` 策略对齐）。
- 每周 OpenSSF Scorecard，目标 Pinned-Dependencies / Dependency-Update-Tool /
  Code-Review / CI-Tests / Token-Permissions 五项满分，总分 ≥ 7。
- `fflate@0.8.2` → `0.8.3`（renderer 已用 0.8.3，命中 GHSA-px8p-9vwx-vf98）。

**验证**：Scorecard 报告；`npm audit --omit=dev` 零 high/critical；
一条「`uses:` 不含可变 tag」的断言（可并进 `architecture.test.mjs` 一族）。

**回滚**：全部是新增配置 + 一个依赖升级；SHA 钉住如果钉错，改回 tag 是单行。

### W3-3 · #8 发布口径

四个独立问题，同批处理：

1. **发布不消费 CI** —— **2026-11-23 已修**：新增 `verify` job（`npm run check
   -- --production` + `cargo test --workspace` + `cargo deny check all`），
   `publish` 改为 `needs: [prepare, runtime, verify, build-installer]`。
   不用 `uses: ./.github/workflows/ci.yml` 复用 workflow——可复用调用拿不到 tag
   的 inputs，而且那会造成「什么叫绿」的第二个事实源。
2. **无安装包构建 job** —— **2026-11-23 已修**：新增 `build-installer` job
   （`windows-latest`，跑 `npx tauri build --target x86_64-pc-windows-msvc
   --bundles nsis`，产物以 `release-candidate-installer` 上传，`if-no-files-found:
   error`）。7 个指向不存在文件的 `pack:*` 脚本已删。
3. **`remote-environments.yml` 必失败** —— **2026-11-23 已删**：它跑不存在的
   `npm run build:remote`、调不存在的 `scripts/build-remote-environment.mjs`，
   服务的是 OMP vendor 的多平台 Runtime 分发，而当前 runtime 是 `step`。已确认无任何
   workflow 或脚本引用它，删除。
4. **未声明的传递依赖** —— **2026-11-23 部分修复**：`warm-release-tools.mjs`
   整个是 Electron 时代的（import 不存在的 `build-installer-host.mjs`、读
   `node_modules/electron`、下载 Electron 工件），已删。`app-builder-lib` 已声明为
   devDependency 并钉版本，两个仍用它的脚本（`build-update-assets-v2.mjs`、
   `verify-differential-download.mjs`）加了注释说明为何只能深路径 import（包根不导出
   `buildBlockMap`）。**残留风险**：上游重排内部布局时 CI 会红而非发布时静默失效——
   Dependabot 现在盯 npm，所以会被抓到，但抓到时仍要人改 import。

另加 SBOM / provenance 随发布物提供（SLSA 的「产物可追溯到一次有门禁的构建」）。

**验证**：红门禁下打 tag，发布必须被拦；Release 里出现安装包；
`npm ls app-builder-lib` 要么声明要么不再 import。

**回滚**：workflow 改动可 revert；删除 `pack:*` 脚本如果发现有人依赖，恢复是单行。

### W3-4 · #9 macOS 进 CI

**根因**：`platform` job 默认只跑 `windows-latest`；`rust` / `rust-shell` 跑 `ubuntu-latest`；
`rust-windows` 跑 `windows-latest`。**没有任何 job 在 macOS 上执行 cargo。**

而壳里的 macOS 分支（`chrome.rs` 的 `open`/`osascript`/权限、`media.rs:801` 的麦克风与 TCC、
`tray.rs:99` 的托盘形态）用的是 `cfg!(target_os = "macos")` **运行时分支**而非 `#[cfg]`，
所以 Linux/Windows 上都会编译、但永远只执行 else 分支。macOS 专属行为只能靠人工真机验。

**修法**：

- 新增 `rust-macos` job：`macos-latest` + `aarch64-apple-darwin`，跑 host / runtime /
  bridge / sessions / tui 的测试与 clippy。
- 把 `chrome.rs` / `media.rs` / `tray.rs` 里可静态判定的分支从 `cfg!()` 改成 `#[cfg]`，
  让「macOS 代码在 macOS 上才编译」由编译器保证，而不是靠人记得在 CI 里加 runner。
- macOS 安装包 job（依赖 W3-3 的 `build-installer` 模式扩展到 `macos-latest`）。

**验证**：`rust-macos` job 绿；一条「`cfg!(target_os = "macos")` 不出现在壳源码里」的断言
（可并进架构测试）。

**回滚**：新增 job + 若干 `#[cfg]` 化，均可 revert。

### W4-1 · #10 前端四道门禁

**根因**：渲染层是产品主体（`App.tsx` 9548 行、161 个测试文件、965 个用例），但零静态检查、
零 a11y 工具、零 i18n 抽取、零覆盖率。

**修法**（四道门禁各自独立，可分批上）：

1. **lint**：引入 eslint（或 biome）。**先只开 error 级 + 少量规则**，别一次开 200 条
   让 281 个文件全红——门禁第一次运行必须是可通过的，否则第一天就被 `--no-verify` 绕过。
2. **a11y**：`eslint-plugin-jsx-a11y` + 一个 `axe` 冒烟测试。先修 issue 点名的三处
   （`ModelConfigPage.tsx:3917/4256/4398`，`role="button"` 无 `onKeyDown`、无可访问名称）——
   这三处比不可聚焦更糟：Tab 能聚焦、按下去没反应。
3. **i18n**：201/281 个 `.tsx` 有硬编码中文，主流写法是内联三元
   `{zh ? "确认完整导出" : "Confirm full export"}`。**不要一次性抽取**——那是 200 个文件的
   机械重构，review 不了。做法：新代码必须走 `t()`；加一条「新增硬编码文案即失败」的门禁
   （只对改动行生效，如 `lint-staged` 或 CI 的 diff 范围检查）；存量按页面分批迁移。
4. **覆盖率**：`c8` 或 `nyc`，先只对 `packages/*` 设阈值，renderer 设「不下降」而不是绝对线。

**验证**：四道门禁各自绿；三处键盘不可达控件修好后有一个 `tab + Enter` 能触发的测试。

**回滚**：每道门禁独立配置，单独 revert。

### W4-2 · #11 兼容策略

**根因**：四个版本号（`STUDIO_PROTOCOL_VERSION = 1`、`CLIENT_CONTRACT_VERSION = 2`、
Runtime 的 `runtime-manifest.json` + `studioProtocol.min/max`、应用版本）各有来源，
不匹配时渲染层只抛一句英文 `UNAVAILABLE`，用户不知道该升级谁。仓库无兼容矩阵。

**修法**：

- `docs/compatibility.md`：谁兼容谁、兼容窗口多长、什么情况拒绝连接、弃用流程（N-1/N-2 承诺）。
- 版本不匹配时给可操作出口：错误码 + 中英文案 + 一键跳转（检查更新 / 重新安装 Runtime）。
- 诊断页显示四个版本号与各自兼容判定，而不是一句 `UNAVAILABLE`。
- 这条依赖 W0-2 的契约表：版本号也是契约，应该进同一张表由门禁保证。

**验证**：手工把 bootstrap 的 `contractVersion` 改成 1/3，渲染层显示可操作提示而非英文堆栈；
诊断页能看到四个版本。

**回滚**：文档 + 渲染层分支，可 revert。

## 四、验收口径

对应 #12 的三级目标态：

| 级别 | 判据 | 由哪些项保证 |
|---|---|---|
| **L1 可发布** | 干净检出 `npm run check -- --production` 与 `cargo test` 全绿；发布只能来自门禁全绿的同一 SHA | #3、#8 |
| **L2 可运维** | 用户报障后 10 分钟内从日志定位到 epoch 与失败分支；日志跨启动保留 | #2、#5（诊断页报原因） |
| **L3 可审计** | SBOM + provenance 随发布物；Scorecard ≥ 7；依赖更新自动化 | #7、#8 |

## 五、未验证清单（不假装通过）

以下项目前**没有**验证条件，方案里不声称已覆盖：

- macOS 专属行为（`open` / `osascript` / TCC / WKWebView / ad hoc 启动路径）——需要 macOS runner 或真机，即 #9 的动机本身。
- Windows 命名管道上的握手、帧编解码、adapter 起 CLI——需要 Windows 真机，见
  [`docs/windows-real-machine-test.md`](../docs/windows-real-machine-test.md)。

  驱动真 CLI，确定性失败于 provider 侧 `auto_retry_start`；**不在** `scripts/core-suites.mjs`
  核心门禁名单内，`npm run check` 不覆盖它。改名前通过、改名后也通过，故不归因于本次整改，
  但它是真实的红，需要一台有有效 provider 凭证的机器才能收口。
