## TLS 选型实测（2026-11-15）：M5.2 更新流程的决策输入

原阻塞记的是「需先定壳是否引入 reqwest……这是产品决策」。实测之后它不再是决策，
是一个有数字的事实。方法：往 `crates/studio-host/Cargo.toml` 加依赖、`cargo update -w`、
数 `Cargo.lock` 的 `[[package]]` 数、`cargo build` 验证。**测完已还原**（595 包，
`git status` 除既有的 scratch 删除外干净）。

| 方案 | 包增量 | 编译 | 备注 |
|---|---|---|---|
| `reqwest = { version = "0.13", default-features = false }` | **+0** | 通过 | 595 → 595。整套 HTTP 栈已在锁里（tauri 的直接依赖），一个不多 |
| 上述 + `features = ["rustls"]` | **+42** | 通过 | 595 → 637 |

### rustls 那 42 个包不只是「多」

拖进来的不只是 TLS 库：

- **`aws-lc-sys` + `cmake` + `fs_extra` + `jobserver`** —— aws-lc-sys 是 C 库，
  **要 cmake 和 C 工具链才能构建**。这是构建环境要求，不是包数问题：
  CI 镜像和贡献者的机器都得有 cmake，而这条不会出现在任何「传递依赖」清单里。
- `ring` —— 另一个 C/asm 库。
- `quinn` / `quinn-proto` / `quinn-udp` —— QUIC，rustls 带进来的，用不到。
- `jni` / `simd_cesu8` / `simdutf8` —— Android 与 UTF 校验，同样用不到。
- `schannel` / `security-framework` —— 平台 TLS，Windows/macOS 上才是活的。

也就是说 **+42 包里真正与「拉一个 HTTPS 索引」相关的只有个位数**，其余是
C 工具链、QUIC、Android 和一个汇编库。

### 另一个坑：特性名不叫 `rustls-tls`

先按常见写法试了 `features = ["rustls-tls"]`，`cargo update` 直接
`failed to select a version for reqwest which could resolve this conflict`。
reqwest 0.13 里它叫 **`rustls`**（`default-tls = ["rustls"]`）。
这个名字在 0.12 及以前是 `rustls-tls`，所以照记忆写会撞墙——
而报错信息指向的是「reqwest 版本冲突」，完全不提特性名，很容易误判成版本问题。

### 结论（供决策）

拉 HTTPS 更新索引的成本不是「40 个传递包」，是 **42 个包 + 一条 cmake/C 工具链要求**。
若接受这条成本，`rustls` 是现成的；若不愿意为「拉一个索引」引入 cmake，
可选的路是让**壳**（而非 daemon）发这个请求——壳是 Tauri 应用，
`tauri-plugin-http` 走的是 WebView 的网络栈，不碰 rustls。
这条路没有实测，记在这里是因为它是这个决策的真实备选项。

## 三个「卡 B1」的判定被推翻（2026-11-15 实查）

上一条记「剩余全部要 Windows 真机（卡 B1）」——**「全部」是错的**。逐条查证后，
本机可做的比台账记的多得多，其中两条是**真 bug**。

### 1 · 升级 marker 读错了目录（真 bug，已修）

`upgrade.rs:9` 的模块文档写「a marker in **the daemon's own state directory**」，
`state.rs:89-94` 也明说 daemon 的状态目录是**机器级**的（一个 daemon 服务全机所有工作区），
而 shell 的 `cwd/.step-studio` 「deliberately not reused for this」。
但 `bin/studio-host.rs` 读的正是后者。

后果：从**非 daemon 自己的那个工作区**触发的更新，写的 marker daemon 永远读不到——
而单实例 daemon 的 `--cwd` 就是第一个壳启动时所在的工作区。文档与实现互相矛盾，
且矛盾的方向是「更新静默失效」。

已改读 `state::state_dir()`。为此把 `state.rs` 的布局拆出 `state_dir_under(base)`：
演练需要给子进程单独设 `XDG_STATE_HOME`（不能 `set_var`，本仓禁 `unsafe`），
于是得算得出**那个** daemon 会去哪里，而不是在测试里重抄一份路径布局。

**非空泛已验证**：把 daemon 读回旧目录，`an_upgrade_marker_drains_the_daemon_that_is_running`
失败（"the daemon did not drain for an update that named it"）。

### 2 · 单实例探测读了一个 daemon 从不绑定的路径（真 bug，已修）

`platform.rs::other_instance_running()` 探 `shell_state_dir()/daemon.sock`，
而 `shell_state_dir()` 是 `<cwd>/.step-studio`（`chrome.rs:285`）；
daemon 绑的是 `lifecycle::default_endpoint()` = 机器级
`/tmp/step-studio-<uid>/daemon.sock`（`lifecycle.rs:53-62`，`bridge.rs:275` 连的就是它）。

后果：生产里探测**恒为 false**，M5.1 的单实例守卫从不触发——第二次启动会开出第二个壳，
而不是退出。而它的测试 `a_second_instance_is_reported_from_the_daemon_endpoint_not_a_new_lock`
是**同义反复**：`assert_eq!(probe, socket.exists() && connect(socket).is_ok())`，
拿函数和它自己选的路径比。路径错了两边一起错，测试照样绿。

已改探 `default_endpoint()`，路径抽成 `daemon_probe_path()`，
测试改成**把路径和 daemon 的 endpoint 比**——这才是它一直想说而说不出口的那句断言。

### #10 · 浏览器捕获读存在 TOCTOU（安全，已修）

`browser_observation.rs` 的计算机捕获读：先用 `symlink_metadata` 查
`metadata.len() > DESCRIPTOR_MAX_BYTES` / `payload.len() > CAPTURE_MAX_BYTES`，

（`File::metadata()` 是 `fstat`，同一个 inode），并且读本身带上限
（新增 `read_bounded`）。这样即使文件在检查和读之间变大，预算仍然成立。

`CAPTURE_MAX_BYTES` 的 payload，断言被拒绝而不是被读进来。原有 11 个测试**没有一条**
盖预算——被绕过的正是没人测的那条。

## M5.7 #13 EXDEV：触发是真的，开出的方子是错的（2026-11-15 已修）

review 记的是「`Upload` 有 `partial` 但没有 `root`，finish 重读 `active_directory()`，
跨文件系统时 rename 报 EXDEV」。**触发属实，方子（copy+delete 回退）不对。**

实查（本机，不是推理）：`/dev/shm`（tmpfs，dev `a42684d7…`）→ `/tmp`（ext4，dev
`5dd07b14…`）的 `rename()` 报 `errno 18 Invalid cross-device link`。`mv` 看不出来是因为它
默默回退到 copy+delete，`rename(2)` 不。把旧行为改回去驱真实代码路径，复现出
`cannot store the artifact: Invalid cross-device link (os error 18)`。

但 copy+delete 是治症状：payload 必须落在它字节已经在的地方，把 64 MB 拷进用户刚离开的
目录、还把行登记在那里，是把问题搬个地方。**根因就是可变全局**——`begin_upload` 与
`finish_upload` 各自调 `library.active_directory()`（重新读盘上的 catalog），而
`set_directory` 接受任意绝对可写路径、不检查文件系统。所以两侧路径不保证同根。

**修法：`commit` 从 `partial` 取目录**（按分量比对 `catalog.roots`，存的时候带尾分隔符
也匹配），rename 只在该目录内，行记那个 `root_id`。EXDEV 从此**结构上不可达**，而不是被处理。
`Upload` **没有加新状态**——partial 路径本身就带着上传开始时所在的那个根，
这正是 finding 要求 `partial` 状态去记的东西，而它已经在了。

### 没人报的另外半边

只修 rename 目标会引入一个新 bug：`commit` 仍从 `catalog.active_root` 取 `root_id`，
于是行指向新根、字节留在旧根——**一个永远解析到缺失文件的 artifact**。
这与 `resolve_refuses_a_payload_that_changed_under_the_catalog` 和
`moving_the_library_keeps_what_was_already_stored` 同形：per-entry `root_id` 机制存在的
理由正是「库移动过之后，不要让它已经写下的东西变成孤儿」。

### 测试

`artifacts::tests::an_upload_streamed_into_one_root_lands_there_even_after_the_library_moves`。
**跑的是真实跨设备 rename，不是缝**：「移动后」的位置是 `/dev/shm`（tmpfs）对库所在的
`temp_dir()`（ext4），用前先验设备号不同；不需要特权、不需要 loopback 挂载、不加依赖。
同设备时（如 macOS）降级为普通目录，不变量断言仍然成立。

三次变异各自红、各自还原：只把 target 改用 active root → EXDEV；只把 `root_id` 改用
active root → `that artifact's file is missing`；两个都改（= 旧代码）→ EXDEV。
第三行是关键：只修 rename 不修行指向，照样坏。
